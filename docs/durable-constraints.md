## Network egress & viewer security

- **The SVG viewer's no-network guard is a `WKContentRuleList`, NOT the nav delegate.** `WKNavigationDelegate.decidePolicyFor` fires ONLY for frame navigations, never subresources — so an attacker-supplied `.svg` with `<image href="https://…">` / `<use href>` / `<feImage>` / CSS `url()`/`@import`/`@font-face` leaked the viewer's IP on mere preview (a real shipped privacy bug — JS-off does NOT stop these passive loads). Fix lives in `SVGViewerView`: a content rule blocks `https?://`, `wss?://`, and host-bearing `file://[^/]` (the protocol-relative `//host` trick) at the *resource* layer; the file load is **deferred until the rule installs** and **fails closed** (don't render) if it can't. Don't "simplify" this back to nav-delegate-only or load before the rule — verified live (a remote `<image>` egress beacon stays unhit while the SVG still renders).
- **Every AVFoundation asset MUST be built via `AVURLAsset.noNetwork(url:)` / `AVPlayer.noNetwork(url:)` (`AVURLAsset+NoNetwork.swift`), NEVER bare `AVURLAsset(url:)`/`AVPlayer(url:)`.** A QuickTime *reference movie* (`rmra`/`rdrf` remote data-ref atom) or an HLS playlist can point a track at a remote URL; without `AVURLAssetReferenceRestrictionsKey = .forbidAll` AVFoundation resolves it on open, beaconing the viewer's IP — and video assets open on mere FOLDER OPEN (thumbnail prewarm) + hero/metadata, so a planted file leaks with no click. `.forbidAll` is inert for legit self-contained local files. **Relatedly, neither a video NOR an AUDIO file may reach QuickLook** (`QLThumbnailGenerator`/`QLPreviewView`): QuickLook's own out-of-process AVFoundation is UNRESTRICTED, so `ThumbnailCache.generate` returns an `NSWorkspace` type icon (not the QL fallback) for a `.video` whose restricted `videoFrame` failed, and `CollectionPDFExporter` frame-extracts videos via `.noNetwork` (never `quickLookThumbnail`). `ViewerRouter` routes `.video`/`.audio` to the restricted players, never `QuickLookFallback`. Don't add a new AV entry point or a video→QuickLook fallback.
- **The QuickLook exclusion covers AUDIO too, and is enforced by `ThumbnailCache.mayUseQuickLook` (2026-07-28).** The video rule stopped at `kind == .video`, but `.m4a` (and the rest of the MPEG-4 family) is the SAME ISO-BMFF/QuickTime container that carries an `rdrf` remote data reference — and audio fell straight through both thumbnail paths (`ThumbnailCache.generate` and `CollectionPDFExporter.fallbackThumbnail`) into QuickLook's unrestricted out-of-process AVFoundation. Thumbnails run on mere FOLDER OPEN, so a planted `.m4a` beaconed with no click: exactly the egress `.noNetwork` closes, through the neighbouring kind. Audio now reads embedded cover art through the reference-RESTRICTED asset (`audioArtwork` / `restrictedAudioArtwork`, bounded by `withinDecodeBudget` so a huge embedded cover can't OOM), falling back to the static type icon — so artwork tiles survive without handing the file to QuickLook. The rule is a predicate both sites consult, not a comment asking callers to behave; a NEW AVFoundation-backed kind must be added to it.

## Google Drive share & the share page

- **The share PAGE makes exactly ONE kind of network fetch — a portfolio's `manifest.json` (2026-07-31).** `connect-src https://www.googleapis.com` in the CSP, `MAX_MANIFEST_BYTES` 512 KB, a 6 s `AbortController` timeout, re-validated through `validateManifest(_, {portfolio: true})`, and the fetched copy's own `m` is DELETED before use — exactly one fetch, never a chain. The inline snapshot renders FIRST and is the fallback on any failure, so the page is never blank because Drive was slow. The page carries a Drive-API-restricted, quota-only browser API key for this; an API key for public data is not a secret, and the binding invariant is unchanged — **no secret and no OAuth credential on the page**. Classic (non-portfolio) shares still touch no network beyond Drive image loads. The committed source keeps `DRIVE_API_KEY = 'REPLACE_AT_DEPLOY'`; the real key is pasted at deploy time only.
- **`e` (expiry) stays REQUIRED for non-portfolio manifests — that is the fail-open guard (2026-07-31).** An absent or malformed date must never yield a never-expiring link by accident. Only a manifest carrying `m` (or a body validated with `{portfolio: true}`, i.e. fetched from Drive) may omit it; those ignore `e` entirely and never take the expired branch. Never loosen this to "optional in general." Manifest v2 keys (`y` layout, `s` body text, `m` manifest id) are optional-only with nil defaults, so a manifest not using a feature encodes NONE of them and legacy fragments decode forever (pinned on both the Swift and node sides). `DriveShareLayout`'s raw values ARE the wire values; an unknown `y` renders grid rather than being rejected.
- **`uploadManifest` is the only non-image Drive upload, and image bytes still reach Drive exclusively through `uploadFile` (2026-07-31).** That's enforced by shape, not convention: `uploadManifest` takes `Data` the caller already JSON-encoded (no file to strip) and pins its mime internally instead of accepting one. Don't widen it to take a URL or a caller-supplied mime — that would make it a strip bypass.
- **Portfolio records use the `neverExpires` sentinel (2100-01-01), never an optional `Date` (2026-07-31).** An optional would make new records undecodable by the PRIOR build, whose failed `load()` silently drops the whole share list on its next save. The sentinel also means `DriveExpiry`/`DriveExpirySweeper` need no portfolio special case — `expiry < now` is simply never true. Every other new `DriveShareRecord` field is optional so a pre-Spec-07 `driveShares.json` decodes unchanged.
- **Portfolio update order is binding: upload-new → `updateManifest` (the atomic cutover) → delete-old (2026-07-31).** Before the swap the page still serves the OLD set, so a failure up to that point rolls back by deleting just-uploaded files and damages nothing; after it, the new set is live. Reordering shows recipients a manifest whose images are already gone. Sweep failures are NON-fatal (`.doneWithSweepWarning`, retried by the next update's sweep). v1 re-uploads every image — no content diffing. The record is upserted in place (same `pageURL`, `manifestFileID`, `createdAt`), and a 404 on the folder is terminal ("publish a new one") — the `drive.file` account-switch orphan doctrine applies to portfolios too.
- **iCloud collection share was REMOVED (2026-06-25) — do NOT re-add it.** The "Share iCloud Link" backend (per-collection copy into `Documents/Shared Collections/`, `NSMetadataQuery` upload wait, "Manage iCloud Shares…") was ripped out because it could not deliver a link: `NSSharingServicePicker` does not offer iCloud's "Copy Link" service for app-container files (that affordance is Finder-only, with no programmatic API), so the share sheet only attached the raw images and email bounced. The deleted units (`ICloudSharePaths`/`ICloudShareStore`/`UploadTally` + the folder-name-safety guards) are gone with it. **The Drive backend (Polish 18) is the only sanctioned collection-link path** — it has a real API. `ICloudZone` stays (it serves iCloud *sync*, a separate feature).
- **Google Drive share security invariants (DO NOT relax).** Scope is EXACTLY `drive.file` (Muse touches only files it created — never broaden to `drive`/`drive.readonly`; that triggers the CASA audit too). OAuth is **Authorization Code + PKCE S256, NO client secret** in the app; tokens live ONLY in Keychain (`…AfterFirstUnlockThisDeviceOnly`, never UserDefaults/logs/synced); sign-out revokes. The share page is a static file with **no API key and no secret** — the manifest rides the URL **fragment** (`#…`, never sent to the host), rendered via `textContent` only with id-regex validation under a `default-src 'none'` CSP. Network happens ONLY inside an explicit user action (sign-in/Publish/Manage/expiry-sweep). **Every uploaded image is metadata-stripped first (`ImageMetadataStripper`, called off-main in `DriveClient.uploadFile`) — GPS/EXIF/camera/IPTC/XMP/maker-notes/embedded-thumbnail all removed, ONLY display orientation kept.** The original is reachable by recipients (the file is anyone-readable AND its id is in the public share URL — the on-page Google thumbnail is EXIF-free but the original isn't), so stripping is a privacy requirement, NOT optional. **Single-frame images RE-ENCODE from decoded pixels (clean by construction — don't "optimize" this back to a lossless container-rewrite; that fail-opens for HEIC/PNG/TIFF where ImageIO ignores the kCFNull strip, the exact bug the adversarial review found). Multi-frame (animated) images take a verified lossless path so the animation survives.** Every accepted output is re-verified clean by `isClean` (field-level property check + raw-byte marker scan — a property re-read ALONE is insufficient; HEIC normalizes the view while bytes keep the data). It's **fail-closed**: a file that can't be decoded or verified throws and aborts the whole publish (folder deleted, no partial/leaky share) rather than upload an un-stripped original. `Output.mime` reflects the ACTUAL bytes (not the extension). Don't remove the strip, weaken it to GPS-only, skip the re-verify, or move it back on-main. **2026-07-03 hardening (keep all):** the stripper pre-checks `ThumbnailCache.withinDecodeBudget` (a decompression-bomb image throws `.tooLarge` instead of OOM-killing the publish); `isClean` walks GIF block STRUCTURE (comment/plain-text/unknown-application extensions = dirty — a naive `0x21 0xFE` byte scan false-positives inside LZW pixel data; "XMP DataXMP" is allowed structurally because ImageIO writes an orientation-only packet on every lossless GIF copy, with its CONTENT vetted by the private-XMP-namespace needles: xap/exif/photoshop/dc/iptc); publish cleanup (`cleanupFolder`) runs in a fresh unstructured Task because a cancelled task's URLSession throws before the network — a direct `deleteFolder` there NEVER deletes, orphaning an untracked folder; the share sheet cancels the publish on ANY dismissal (`onDisappear`) or the upload continues headless and goes public unseen; `DriveShareService` phase writes are generation-guarded (`setPhase(_:ifCurrent:)`) so a superseded run can't clobber a re-publish's UI; Drive share sends raster images ONLY (`.image/.raw/.psd` — a PDF/video file card would abort the whole publish fail-closed), with per-file strip failures surfaced by filename (`PublishError.unshareableImage`); "Open Link" in Manage validates `record.pageURL` against `shareBaseURL` before `NSWorkspace.open`; `GoogleOAuth.authenticate` resumes its continuation when `ASWebAuthenticationSession.start()` returns false (otherwise sign-in hangs forever) and cancels the browser sheet when its task is cancelled. **Out of scope (platform-inherent, NOT fixed by the strip — disclose, don't pretend otherwise): a recipient can read the sender's Google account name/avatar via the Drive API on the file ids, and filenames ride the manifest as captions.** Expiry is **Muse-local** (launch sweep deletes the Drive folder it created). The recipient's PDF is the **printed page** (`window.print()`), no app-side PDF. Files live in `Sharing/Drive/`; the page in `web/share/` (deployed to `muse-share.pages.dev`). **Sign-in/out is a Settings row** (`SettingsView` "Google Drive" section); `prompt=select_account` lets a user switch accounts. **Account-switch leaves the OLD account's share folders orphaned (by design, NOT a bug):** `drive.file` is account-scoped, so once signed into a new account Muse can't see/delete the old account's folders — the expiry sweep + manual delete treat the resulting 404 as success and just drop the local record (the page still soft-expires). To truly clean up, delete shares via Manage Drive Shares BEFORE signing out. `signOut()` clears `driveRootFolderID` so the new account gets a fresh root.
- **Share manifest may be DEFLATE-compressed + carries per-image filenames — decode MUST cap the inflate (zip-bomb guard).** The fragment now encodes either raw JSON or `[0x01 marker][raw-DEFLATE(JSON)]` (the app picks whichever is shorter, so filenames — key `f`, 1:1 with image ids — don't bloat the link). Raw DEFLATE = Swift `COMPRESSION_ZLIB` ⇄ vendored **fflate** `inflateSync` (`web/share/fflate.module.js`, MIT, pure-compute/no-network — keep it that way; legacy uncompressed links `{`-first still decode). The fragment is unsigned + attacker-suppliable, so `decodeManifest` inflates into a **bounded** `MAX_INFLATED` buffer — a decompression bomb truncates to garbage → `null`, never an unbounded allocation. Don't remove the cap, don't broaden the CSP for fflate (it's a `'self'` ES-module import), and `f` must stay length-matched to `g` (mismatch → captions dropped, not mis-paired). All attacker-supplied display text (filenames + signature) renders via `textContent` AND through `sanitizeText` (strips bidi-override/zero-width/control chars — anti-spoofing) with per-field length caps; ids are upper-bounded (`{20,200}`). Grid tiles are `<button>`s (keyboard-operable → lightbox), and the caption uses the AA-contrast `--caption` token (not `--muted`). Don't relax these.
- **The Drive multipart `mime` is token-validated (`DriveClient.isValidMIME`) before it reaches the `Content-Type` header** — it's interpolated raw, so a CR/LF-bearing value could forge headers/parts; off-grammar collapses to `application/octet-stream`. Every current source is a UTType-registry value, but keep the guard so a future caller can't turn it into a CRLF-injection foothold.

## Export & the output choke point

- **Social export renders through `OutputRender.forOutput` FIRST, never upscales, and bakes orientation at decode (2026-07-31).** Pipeline order is code: choke point → `withinDecodeBudget` → ImageIO decode with `kCGImageSourceCreateThumbnailWithTransform` at `min(source, max(4096, 4 × output long edge))` → fit compose → `CILanczosScaleTransform` → `CIUnsharpMask` ONLY when a downscale happened → flatten → 8-bit sRGB → JPEG with the byte-target ladder → `EditCopyNaming`-style collision ladder. Baking orientation is what makes "no output orientation tag can exist" structural. A default-metadata output must PASS `ImageMetadataStripper.isClean` before it's written (verify, don't trust construction). **The X preset's five invariants are test-pinned — ≤4096², <5 MB, RGB/no-alpha, no orientation tag, bytes < W×H — and the ladder is driven off the invariants themselves, not off a byte target (X has none); a source that can't meet them even at the 0.55 floor FAILS that file rather than shipping a recompressible one** (`XPresetRuleTests` pins both directions). Never trade an invariant for quality.
- **Nothing in the social export card persists unless the user explicitly saves a version (2026-07-31).** Crop positions, zooms, fit modes and the location toggle all die with the card. The remembered bits are exactly three: per-preset-id EXIF choice (`AppSettings.socialExifChoices`), matte shade (`AppSettings.socialMatteShade`), share layout (`AppSettings.driveShareLayout`). **GPS is a sub-toggle of the EXIF toggle, defaults OFF and is NEVER remembered.** "Save Crop as Version" is the one opt-in: it composes via `SocialCropMath.composedCrop` and writes ONE `edit_versions` row through `EditStore.saveVersion` — the current stack is untouched, and there is no new write path. The crop-stage preview decodes DIRECTLY at ≤2048 through `withinDecodeBudget` — no `ThumbnailCache` entry, no `renderedVariants` change (the compare-pane rule).
- **Everything that leaves the app goes through `OutputRender` (2026-07-31).** PDF export, Drive publish, and both share-sheet paths take a `RenderedOutput`, never a bare `URL`; `RenderedOutput`'s `fileprivate` init is the enforcement — a new export/share/publish path physically cannot compile without going through the choke point. It's an identity function today (originals pass through unrendered); Spec 04 renders the edit stack in that ONE place and every call site is already correct. Don't relax the init, don't add a public one, and don't let a new path take a `URL`. The Drive path renders FIRST and strips SECOND (`ImageMetadataStripper.strip(_:mime:)`), so no future edit can reintroduce metadata past the stripper. **Backup is the one deliberate exclusion** — it restores originals matched by content hash, and baking edits into the archive would corrupt the restore (noted in `BackupBuilder.swift` too, so the exclusion is findable from either direction). Non-rendering fallbacks (a video frame, a QuickLook type icon) legitimately keep taking a `URL` — they carry no edit stack.

## Import & migration

- **Every import writes through EXISTING seams only — a new source is a reader and a mapper, never a new writer (2026-07-31).** Tags via `MetadataImportApply.applyKeywords` (insert-or-promote manual, rating glyphs dropped), ratings via `TagStore.setRating` behind `MetadataImportRules.ratingToApply` (gap-fill), notes via `NoteStore` (fill-gaps — an import never overwrites what the user typed), edits via `EditStore.save` (never clobbers an existing stack — which is also what makes re-runs idempotent), collections via `CollectionStore.createManual`/`addFile`. `AppState.importModal` REPLACED `metadataImportRequest` 1-for-1 (net-zero `@Published` count) and every card — run, label mapping, report — is a PHASE CHANGE of that one flag, never a card stacked over a card. Spec 06 adds NO migrations; future specs continue at v24.
- **Label tags carry the canonical-English `"Label: "` prefix and are EXCLUDED from the free-text tag-search leg unless the query names them (2026-07-31).** Lightroom's red *label* is a workflow marker; Muse's red is a content attribute (palette/colour search). `LabelTag.isLabel`/`queryTargetsLabels` gate the exclusion inside `SearchService`'s tag leg — "red" must never match `Label: Red`, "label: red" must. `LabelMapping.resolvedLabel` refuses a ★-run mapping target INSIDE the mapper (not per caller), the same placement as `TagSuggest.rank`'s rating filter. Choices persist keyed by the RAW source string, so a French catalog's "Rouge" is deliberately a distinct key from "Red"; all-remembered means the sheet is skipped silently. The label chip renders OUTLINED with a `tag` glyph because it means something different, and dismissing the mapping card resolves the suspended run as Skip All rather than stranding it.
- **`ImportSupplement` is the ONE writer for externally-sourced GPS/dates, header-wins/external-fills-gaps, stamping BOTH scan markers (2026-07-31).** XMP sidecar GPS, Takeout JSON and `PHAsset` all route through it. Stamping `coords_scanned_hash` AND `photo_meta.exif_scanned_hash` is what makes Spec 02's amendment A1 (already live in `AnalyzePipeline.writePhotoHeader` — skip the write when both markers are fresh) stop the next analyze pass clobbering an imported coordinate with the header's NULL. `(0,0)` is ALWAYS absent, never null island; the write is row-guarded on `content_hash`. Recorded limitation: an edit-in-place stales the markers, the header is re-read, and supplement-only values drop until re-import.
- **The Lightroom import envelope is the enumerated field list in `LightroomXMP` and may not grow without a foundation-doc change (2026-07-31).** Translated: crop/CropAngle/orientation (exact geometry), WB, Exposure2012, Contrast2012, Vibrance, Saturation, tone curves. Highlights/Shadows/Whites/Blacks/Clarity/Texture/Dehaze/grain/post-crop vignette/local corrections/retouch/looks are DETECTED ONLY, for the report's disclosure — they are image-dependent operators whose Adobe implementation is unpublished, so translating them produces a picture that is confidently wrong (darktable skips them; Capture One approximates ~6 sliders). The process-version gate is KEY PRESENCE (`2012` suffixes), never `crs:ProcessVersion` parsing. RAW WB reads the RENDERER's own `MiredMapping.maxMiredOffset` — one constant, so an imported number means what the slider means — and is SKIPPED (not guessed) when the as-shot neutral can't be read. The importer never pins `rawParams.decoderVersion`; the first USER edit does.

## Editing engine

- **`EditStack.origin` is provenance, not data (2026-07-31).** nil-omitted by synthesized `Codable`, so every pre-existing stack's canonical bytes and `stack_hash` are byte-identical (`EditStackOriginTests` pins that the key is absent). Never copied by `EditTransfer.apply` (the target keeps its own), stripped by `EditPresetStore.presetJSON`, gone on Reset. The LR PRESET importer keeps it via the separate `createImported` path — that look genuinely is an approximation of someone else's, and the badge is how the user knows. An older build decodes the key away harmlessly.
- **New `Adjustment` cases APPEND, and Spec 05's two are `toneZone` then `lut` (2026-07-31).** `canonicalIndex` 6 and 7, after `.vignette`. Inserting either mid-list re-keys every pre-existing edited thumbnail's `stack_hash` in every library; `EditStackCodecTests`' Spec 04 pinned fixture is the tripwire. `schemaVersion`/`currentProcessVersion` both STAY at 1 — a new enum case is the wrapper's designed forward-evolution path (an older build decode-fails the stack and renders the ORIGINAL, blob preserved), and bumping either would make older builds refuse stacks they can read. The chain order is now `1 geometry → 2 tone/WB → 2b toneZone → 3 curve → 4 color → 4b lut → 5 presence → 6 vignette`; `toneZone` is scene-referred, `lut` is the SECOND display-referred pocket (after the curve) because `.cube` packs are authored against display encoding.
- **LUT rows are IMMUTABLE and an unresolvable LUT renders the ORIGINAL, never a partial stack (2026-07-31).** `edit_luts` (v23) is content-addressed — the PK is `CubeLUT.hash`, SHA-256 of the canonical float bytes — so import is `INSERT OR IGNORE` (re-importing under a new name dedupes, first name kept), rename touches `name` only, and there is no update path: a `lutHash` resolves to byte-identical data or to nothing. `EditRenderer.canRender` gates on resolvability, so a missing LUT falls back to the original everywhere (thumbnails/hero/exports) and re-importing the same `.cube` heals every referencing photo at once, filename-independent. `LutRegistry` is RENDER-PATH-ONLY (a miss is a synchronous multi-MB `queue.read`) with an 8-entry LRU — never library-resident, never called on the main thread; `preload` seeds it straight from a just-parsed cube. `CubeLUTParser` REFUSES a non-default `DOMAIN_MIN/MAX` (`unsupportedDomain`) and `LUT_1D_SIZE` rather than resampling — a resampled look is a different look under the original's name. R fastest-varying is pinned by an asymmetric fixture. Render is `CIColorCubeWithColorSpace` with an EXPLICIT sRGB space (bare `CIColorCube` shifts on P3) + `extrapolate`; strength rides the `lutMix` kernel. LUT blobs never ride sidecars.
- **Zebras, the live clipping percentages and the Scopes messages read ONE pair of thresholds; stored capture stats read a DIFFERENT, fixed pair (2026-07-31).** `AppSettings.editorZebraHigh`/`editorZebraLow` (0.98/0.02) are shared by all three live surfaces, so their agreement is structural rather than maintained — never fork the constant. `photo_traits.clip_high_r/g/b`/`clip_low` (v22) use `ClippingStats.storedHighThreshold` 254/255 and `storedLowThreshold` 2/255 and must NEVER read the prefs: a stored row would otherwise change meaning when a slider moves. The zebra TOGGLE is session-scoped (`EditSession.zebrasOn` + J in Edit mode), never persisted; only the thresholds persist. Raw-sensor (pre-demosaic) clipping is SKIPPED, not approximated — `CIRAWFilter` exposes no cheap tap, and display clipping is what the stripes mean.
- **Editor statistics compute ONLY while a consumer is visible, piggybacked on the render that just completed (2026-07-31).** `EditSession.statsVisible` is true for the Light or Scopes tab in Edit mode and never in Preview; the tap runs at `statsSampleLongEdge = 256` off-main after `renderDraft`, never a second render loop and never full-res. `applyStats` writes `stats` and `zoneEVMap` TOGETHER so a panel can't draw a histogram from one frame beside zone mass from another, and `zoneEVMap` is deliberately NOT `@Published` (a per-render buffer publish would re-render every observing panel for nothing — hover reads it imperatively). The zone tap samples `EditRenderer.toneStageImage` — chain position 2b's own input — so the strip, the hatch and the render describe the same pixels.
- **The tone zone's guide is edge-aware, scale-normalized, and shared by three consumers (2026-07-31).** `ToneZoneFilter.smoothedEVMap` (log2-luma guide ≤1024px, self-guided guided filter, `guidedRadiusFraction 0.05` × long edge, `guidedEpsilon 0.25`) serves the render stage, the stats tap and the zone overlay — one mask, by construction. Application is `exp2(Σ wᵢ·gainᵢ·maxZoneEV)` as a SINGLE gain on RGB, so hue survives by construction and zero gains are an exact identity. `ToneZoneMath`'s raised-cosine weights are a partition of unity: equal gains across all nine zones is exactly a plain exposure shift, which is the property `EditRenderNeutralityTests` asserts end-to-end (a fixture-specific zone would depend on where a test image's pixels happen to land — `CIColor` clamps to 0…1, so a negative-EV fixture silently becomes 0). Direct manipulation lives behind an explicit TARGET MODE because plain scroll must keep zooming the canvas; Escape consumes targeting INSIDE the hero's edit-mode branch before exiting to Preview (`EscapeResolver` untouched). The accessible path for the strip IS the disclosed nine `EditSlider`s — the drag needs no parallel accessibility action.
- **Photo feedback is a deterministic rule table, never an LLM, over precomputed columns ONLY (2026-07-31).** `PhotoFeedback` reads `photo_meta` + `photo_traits` through `PhotoStatsQueries.feedbackInputs`, inside passes that are already off-main — the surface must never trigger a decode or query-time analysis. Fixed severity order (clipping → shadows → motion → noise → soft → thin focus), `maxNotes = 3`, and an EMPTY result renders NO card: silence about a well-exposed photo is the correct output, not a fallback state. Flash suppresses the motion-blur note (the flash IS the exposure); motion blur suppresses the soft-focus note (cause beats symptom — one blur, one explanation). Absent fields never fire a rule. The table is Swift-declared, not a data file: string extraction can't see a data file, and these sentences localize like everything else.
- **`EditRenderConsistencyTests`' all-groups fixture must include EVERY renderable group, current and future (2026-07-31).** `toneZone` and `lut` are in it now; a new chain stage lands inside the standing 3-resolution thumbnail/screen/export gate in the SAME commit that adds it, or a scale-dependent radius ships unnoticed. The LUT fixture resolves via `LutRegistry.preload` rather than a DB row, so the gate never touches the user's library.
- **The edit stack is per `(file_id, parent_dir)`, and a NEUTRAL stack is a DELETED row (2026-07-31).** `edits`/`edit_versions` (v20) and `edit_presets` (v21) join tags and notes at the per-location grain — never a column on `files` (`content_hash` is UNIQUE, so two folders' copies would share one stack). "No edit" is the ABSENCE of a row, which is also what reverts the thumbnail key to its unedited variant; never store a no-op blob. `EditRecordStore` mirrors `NoteStore` exactly and is called BESIDE the existing `NoteStore` call at all five rewrite seams (Indexer hash-collision sole-path `carryAll`, hash-collision shared-row, shared-row split, `FileMoveMigration.apply`, `FolderRenameMigration.apply`'s pre-clear + `SUBSTR`-prefix rewrite). Carried `edit_versions` rows get FRESH UUIDs — reusing the PK silently drops every version but the first when two scopes merge. A pure edit-in-place KEEPS its stack (parameters are normalized, so they still apply; discarding a user's edits because bytes changed is the worse failure). Any NEW path rewriting `file_id`/`parent_dir` must carry `edits` too.
- **`Adjustment`'s DECLARATION ORDER is canonical and new cases must APPEND (2026-07-31).** `EditStack.normalized()` sorts/dedupes by it, `EditStackCodec` encodes `.sortedKeys` JSON of the normalized stack, and `stack_hash` is SHA-256 of those bytes — so inserting a case mid-list re-keys every edited thumbnail in every library. `EditStackCodecTests` pins the hash against a literal fixture; that failing is the tripwire. Decoding NEVER bumps `schemaVersion`/`processVersion` (only `EditStack.fresh()` stamps them), an unknown adjustment `type` fails the WHOLE decode (that IS the forward-compat mechanism — an older build renders the ORIGINAL, blob preserved), and a `processVersion` beyond ours decodes but `EditRenderer.canRender` is false. **An unrenderable stack renders as the ORIGINAL, never partially, and its blob is never rewritten** — only an explicit user edit or Reset overwrites it.
- **The render chain's ORDER is code, never data, and every scale-dependent radius is a FRACTION of the long edge (2026-07-31).** `EditRenderer.apply` iterates its own fixed chain (geometry → tone → curve → color → presence → vignette); the stack is parameters, and reorderability is deliberately unrepresentable. Scene-referred throughout except the curve, which is the one display-referred pocket (a monotone Fritsch–Carlson `CurveLUT` → `CIColorCurves` with an explicit sRGB space; `CIToneCurve` is never used anywhere). Highlight data above 1.0 must survive to the display transform or highlight recovery silently does nothing — `HighlightRecoveryTests` pins it, and its fixtures are FLOAT bitmaps because `CIImage(color:)` clamps (a `CIColor`-built fixture makes that whole file pass vacuously). A pixel radius instead of a fraction makes a thumbnail and an export disagree: `EditRenderConsistencyTests` (one all-groups stack × 2 fixtures × 3 decode resolutions) is the permanent gate on any renderer change.
- **RAW white balance happens ONLY at demosaic, and the mired range is DERIVED from the floor (2026-07-31).** `RawSource` zeroes Apple's default look (`baselineExposure`/`shadowBias`/`boostAmount`/`localToneMapAmount`, `isGamutMappingEnabled = false`) and routes the SAME `ColorParams`/`PresenceParams` sliders into `CIRAWFilter` — never `CITemperatureAndTint` on a RAW source's output, and `EditRenderer` skips its own WB/NR/sharpen stages when `rawParams` is present so nothing is applied twice. `MiredMapping.maxMiredOffset = d65Mired - miredFloor` on purpose: picking a warm target Kelvin independently runs the cool side past the floor, clamps, and makes the slider quietly warm/cool asymmetric (the Surface Camera bug). Temperature/tint map in MIRED, never raw Kelvin.
- **`EditStackIndex` reads its provider OUTSIDE the lock (2026-07-31).** `NSLock` is not recursive and `LiveEditStackProvider` reads the same index, so holding the lock across the provider call deadlocks the first time anything asks an edited file for its hash — i.e. every grid tile, on the main thread. Only the provider REFERENCE read needs mutual exclusion. The index itself is pre-resolved at rebuild time (hash, decoded stack, geometry, renderable) because it's consulted from view bodies and off-main thumbnail workers: the provider does NO I/O, ever. `warmIndex(paths:)` passes `clearingScope:` so a reset REMOVES the entry — without it a reset photo keeps rendering its old stack until the next full rebuild. An UNDECODABLE blob resolves to no stack but still reports its hash, so a later build that can read it doesn't serve the original's cached PNG forever.
- **The edit save sequence is one place, in order, and index-before-invalidate is load-bearing (2026-07-31).** `EditStore.save`: resolve scope → `EditRecordStore.write`/`delete` → `warmIndex` → `markContentChanged` → `generation += 1` → `exportSidecarsAfterEditChange`. `markContentChanged` derives the EDITED cache-key variant from the index, so invalidating first clears the old pair and leaves the new stack's PNGs live. `EditStore` has zero AppState integration — no forwarded `objectWillChange`, no new `@Published` on AppState; the grid reads `EditStore.generation` through the existing `gridSignature` string (a crop changes tile aspect, so it must relayout). Its one weak `host` reference exists solely to call `markContentChanged`, the app's single tile-refresh seam. The editor AUTOSAVES (400 ms debounce + save on exit); there is no Done/Cancel, because the grid updates live and Cancel couldn't honestly promise to put it back.
- **The sidecar's edit field has its OWN clock and is owner-gated (2026-07-31).** `Sidecar.edit_stack`/`edit_updated_at` default nil so pre-edit sidecars decode unchanged. `merge` resolves them by `edit_updated_at` (greater non-nil wins, nil never clobbers) — NOT the sidecar-wide `updated_at`, or a newer analyze-export from a device that never saw the edit rolls it back. Only `exportSidecarsAfterEditChange` passes `editAuthoritative: true` (fresh wins INCLUDING a clear, which is how a Reset propagates); every other export preserves the on-disk value. Hydration applies via `EditRecordStore.applyHydrated` (row-level LWW, strictly-newer local wins) and is SKIPPED entirely when the sidecar carries no edit clock — no clock says nothing about edits, and treating it as a synced reset would delete them. Versions/snapshots are device-local and don't ride sidecars.
- **The editor is a STAGE SWAP inside the hero viewer, and Edit-mode Escape returns before the close runs (2026-07-31).** Entering Edit replaces the stage's content and hides the info column; the open/close flight, the parting ripple, the backdrop fade and every guard in `loadFullRes` are untouched. The Escape branch is FIRST in the `viewerClosing` onChange and RETURNS — one press leaves the editor, a second closes the viewer. Arrow-key file flips are inert in Edit mode (they'd swap the file out from under an in-flight edit). Editable kinds are `.image` and `.raw` ONLY: `.psd`'s flat composite is a PREVIEW of a layered document, so editing it belongs to Edit-a-Copy. Grid badge corners are now fully assigned — top-leading stack · top-trailing star · bottom-leading cull · bottom-trailing edited (`slider.horizontal.3`, count appended when versions exist, never a click target).
- **Every external hand-off of an edited file forks through `OpenWithFork` (2026-07-31).** Muse edits live in the database, not the file, so "Open With" on an edited photo hands over the ORIGINAL and the reasonable conclusion is that Muse discarded the adjustments. Every Open / Open With call site routes through the one seam; an unedited file opens exactly as before with no extra click. `EditCopyFlow` is ordered and fail-closed (render to a TEMP → forward EXIF minus orientation → move → `Indexer.indexFile`): a failure before the move writes nothing, and one after it leaves a real file the next reconcile finds. RAW copies render 16-bit TIFF (external editors can't write RAW back); the copy is a FRESH asset with no inherited stack. Metadata stripping is a Drive-SHARE rule, not a local one — an edit-copy keeps its capture data.
- **Presets store stacks MINUS geometry; copy/paste is copy-by-value (2026-07-31).** A stored crop ambushes every photo a preset is applied to, so geometry is excluded at the single `EditPresetStore.presetJSON` seam — and it is the ONLY exclusion (copy/paste, a deliberate one-off, does offer it). No stack ever stores a preset reference; preset mutation happens only via explicit "Update Preset from This Photo" / "Save as New". `EditTransfer.apply` clears a group that's absent in the source (otherwise pasting a neutral look appears to do nothing), and `EditClipboard` is in-memory only — never `NSPasteboard`, never persisted. The batch sweep snapshots the clipboard up front so a mid-run change can't apply two different looks, and runs the FULL save sequence per file (tiles refresh as it goes; no progress UI — the status pill stays background-work-only).
- **`Editing/` imports Foundation/CoreGraphics/CoreImage/Metal ONLY (2026-07-31).** `EditingModuleImportTests` greps for `AppKit`/`SwiftUI` there. Caveat before you "fix" a skip: the test HOST is the sandboxed app, so it can only read the source tree when the checkout sits outside `~/Documents`/`~/Desktop`/`~/Downloads` — it SKIPS rather than passing vacuously when the read is denied, and a green run on a checkout elsewhere is the real gate. Relatedly, `Views/Editor/`'s `EditCanvasView` (MTKView + `CIRenderDestination`) and the `[[stitchable]]` kernels in `EditKernels.metal` are the app's sanctioned Metal surface — which supersedes the older "no Metal shaders remain" note (that was about the removed water/burn effects). Stitchable Core Image kernels need `extern "C" [[stitchable]] float4 name(...)` (the attribute goes before the RETURN TYPE; after it the compiler reports "cannot be applied to types"), compile into the default metallib with NO `-fcikernel`, and a nil kernel SKIPS its stage rather than crashing — `EditKernelLoadTests` is what makes a broken Metal build phase fail in CI instead of at first slider drag.

## Photo metadata, geocoding & stacks

- **One header pass serves GPS AND EXIF: `PhotoHeaderReader` (2026-07-31).** Supersedes Spec 01's `CoordinateReader`/`CoordinateBackfill` (both deleted). Key handling MIRRORS `FileMetadata.imageMetadata` exactly — the same prefix-stripped bare keys via the same `sub()` shape, the same `ISOSpeedRatings` array-or-scalar tolerance, the same `FileMetadata.coordinate`/`parseISO6709` calls — because a viewer showing one camera/location while search indexes another is the failure this prevents. `AnalyzePipeline.writePhotoHeader(db:fileID:hash:header:)` is the single write seam (nonisolated, so the backfill can call it inside its own transaction); it stamps BOTH attempted-markers (`files.coords_scanned_hash`, `photo_meta.exif_scanned_hash`) even when the header carried nothing, and SKIPS the write entirely when both already equal this content hash — an unconditional re-write would clobber externally-supplied GPS/date with a re-read producing NULLs. The video branch runs BEFORE the image-kind guard and pre-checks both markers before opening the file (videos never get `analyzed_hash`, so `analyzePending` re-queues them every folder visit).
- **`capture_md` is MATERIALIZED, not `strftime` at query time.** A `strftime` WHERE clause can't use an index; On This Day depends on the index. Same rule as every other "query time touches only precomputed data" decision, applied at schema level.
- **Geocoding is offline, and the GeoNames dataset is never cached (2026-07-31).** `GeoNamesDataset.cities()` re-parses the bundled artifact on each call and hands the array to the caller, who holds it for exactly one geocode pass — browsing carries zero standing cost for ~7 MB of place data. The bounded inflate (declared size in the first 4 LE bytes, allocate exactly that, mismatch → nil) fails closed. `CLGeocoder`/MapKit geocoding are forbidden (network + throttled); `maps://` and `https://www.google.com/maps?q=` via `NSWorkspace.open` are browser hand-offs, never touched with `URLSession`. `GeoKDTree` is 3-D over unit-sphere Cartesian coordinates, NOT 2-D lat/lon — chord distance is monotone in great-circle distance, so nearest-neighbour is exact and the antimeridian/poles stop being special cases. **The bundled `Resources/geonames-*.tsv*` are PLACEHOLDERS (9 cities)** until the owner runs `scripts/make-geonames.sh`; bump `GeoNamesDataset.version` when they do, which re-geocodes the library.
- **Stacks are presentation-only, and `dissolved` is a permanent tombstone (2026-07-31).** `stacks`/`stack_members` hold content-keyed sets of `file_id` — no `parent_dir`, no path — and stacking never touches tags, ratings, notes, collection membership, paths or `analyzed_hash`. Unstacking sets `dissolved` and KEEPS the members, because `StackStore.claimedFileIDs` (which includes dissolved members) is what makes a file off-limits to the auto-stacker forever. Don't "clean up" dissolved rows. `BurstClusterer` buckets by TIME first (10 s session gap) and similarity second, and its oversized-session splitter breaks ties toward the MIDPOINT — splitting at index 1 on a run of evenly-spaced frames peels one item at a time and never bounds anything. **Collapse applies ONLY in plain folder browsing** — never search (a matching frame must not hide under a non-matching representative), collections or rediscovery; `StacksStore.badges` is a PLAIN var written inside the memoized `visibleFiles` computation and must not publish.

## Indexing & file identity

- **A shared `files` row must SPLIT on edit-in-place, never be rewritten.** Two byte-identical files in different folders dedupe onto one `content_hash`-UNIQUE row. `Indexer.reconcile`'s edit-in-place branch only rewrites the row in place when it's the SOLE alive path; when >1 alive path shares it, it splits (new row for the edited path, carrying that location's tags AND its manual collection memberships) so the untouched sibling isn't corrupted and the two copies don't ping-pong the shared hash. Don't collapse the split branch back into an unconditional in-place update (`IndexerReconcileTests` guards both directions + the membership carry). **The hash-COLLISION edit branch (new bytes match a different existing row) follows the same rule** (2026-07-03): when the old row is shared, only THIS path's folder-scoped tags carry to the target (copy-vs-move by the same same-dir-sibling rule) and manual memberships copy — an unscoped `unionTags` stripped the untouched sibling's tags. `unionTags(parentDir:deleteOriginals:)` is the scoped seam; +3 collision tests guard it.
- **A recursive walk that diffs against the DB MUST carry its unreadable directories (2026-07-28).** `FileManager.enumerator` with a nil error handler skips a directory it can't open in TOTAL silence — no error, no partial results (verified against a chmod-000 subfolder: the directory is yielded, its children simply never appear). So absence from the enumerated `present` set is only evidence of deletion where the walk actually looked. `reloadCurrentFiles`'s `trustworthy` probe proves only the TOP folder is listable; in subfolders-ON mode one unreadable/not-yet-materialized subfolder made `PathReconciler.reconcile(recursive: true)` flip every row beneath it to `is_alive = 0` — the mass-false-deletion class, and those rows can then be permanently pruned with their tags and notes. `enumerateRecursiveScan` now returns `unreadableDirs` (the root itself when the enumerator can't even be created) and `reconcile` drops candidates under them via `excludingProtected` (trailing-slash bounded, like every prefix test here). Don't call `enumerateRecursive` for anything that DIFFS against the database — use the scan and pass the dirs through. `showHidden` is always false and has no UI, so hidden files are never indexed and need no equivalent guard; that changes the day it becomes user-facing.
- **`Indexer.indexFile`'s body must stay `nonisolated` (2026-07-28).** It was an isolated *synchronous* actor method, so it never suspended and ran to completion under the actor's lock: `hashConcurrency = 4` bought nothing (measured peak concurrency: **1**) and every file's SHA-256 serialized behind the previous one, while `inFlightHashes` was unreachable dead code (set and cleared with no suspension point between, so it could never observe a duplicate). Only the claim/release bookkeeping needs isolation. The reconcile's atomicity comes from GRDB's `DatabaseQueue` — one connection behind a serial dispatch queue, so all reads AND writes serialize regardless of calling thread, and the whole matrix runs inside one `queue.write` transaction — NOT from the actor. Re-isolating the body silently reverts indexing to 1-wide. The claim is released inline, never via `defer` + an unstructured `Task` (the next pass over the same file would race the release and be skipped).
- **`PathReconciler.reconcileByExistence` MUST fail closed on an unreachable root.** It clears deep ghost `is_alive` rows a browsed-depth `reconcile` can't reach (files whose whole subfolder was deleted — e.g. leftover `Documents/Shared Collections/` copies from the removed iCloud-share feature) by per-file `fileExists`, dataless-safe. But if the ROOT is transiently unreachable (unplugged volume, un-materialized iCloud container on cold launch, stale bookmark) EVERY child reports gone → the whole subtree would mass-flip `is_alive=0`, and it runs PROACTIVELY at launch on every root incl. the never-selected iCloud one (deep files it kills are never revived by browsing). The `rootReachable` gate (`contentsOfDirectory` succeeds) is load-bearing — returns `ExistenceResult(reachable:false)` and touches nothing when the root can't be listed; the caller releases its once-per-launch `existenceReconciledRoots` claim on `!reachable` so it self-heals on a later rebuild. Don't remove the gate, and keep it FIRE-AND-FORGET (`Task {…}`) off the grid's critical path — awaiting the full-subtree stat sweep stalls the folder-load publish (`PathReconcilerTests.testReconcileByExistenceBailsClosedOnUnreachableRoot` guards this).
- **`Housekeeping.pruneUnreachable` is a PERMANENT DELETE — it must fail closed on root visibility (2026-07-03).** The launch call site skips the prune unless EVERY persisted bookmark root resolves (an unplugged volume / stale bookmark would read as "unreachable" and purge its whole subtree), and the iCloud "Muse" root — never a bookmark root — is resolved directly and passed via the `icloudRoot` param; when THAT can't resolve (signed out, Debug build), any `/Mobile Documents/` path is protected wholesale. Same guard class as `PathReconciler.rootReachable`, stricter because rows don't come back. `HousekeepingTests` pins all of it.
- **In-app file moves go through `AppState.moveFiles` ONLY — never call `FileMover.move` directly (2026-07-03).** `moveFiles` runs the disk move off-main, then `FileMoveMigration` (repoint the alive path row + carry the location's tags, MANUAL included, copy-vs-move by the same-dir-sibling rule, Q32 merge at the destination, stale-alive-row pre-kill for `paths_alive_unique`), then re-exports iCloud sidecars. An in-app move is a KNOWN relocation; bypassing the migration silently degrades to external-move semantics (vision-only tag inherit). `FileMoveMigrationTests` guards the shapes.

## iCloud sync & sidecars

- **iCloud change detection = content hash, NOT size/mtime.** iCloud oscillates size/mtime on repeated reads, so a size/mtime fast-path reindexes the whole folder every visit. In-place edits are re-checked via content hashing (FSEvents live + cold-open verify) — deliberate. The zero-byte-hash guard in `HashService.sha256` must stay (its loss welded 900+ files onto one row). Memory: `muse-icloud-content-refresh-override`.
- **Classification never reads dataless iCloud bytes.** `AssetKind`'s ImageIO header sniff (extensionless-image fallback) guards on `.ubiquitousItemDownloadingStatusKey` and skips not-downloaded placeholders — reading bytes would force a download to classify a file the user is just browsing. Reclassifies once local. Same spirit as `Indexer.isDataless` / `HashService` dataless-nil.
- **iCloud container is data-loss-sensitive.** Debug builds sign with `*-Debug.entitlements` (production minus the three iCloud keys) so dev churn can't make `bird` purge the production ubiquity container. Ship updates via **Sparkle only** (atomic in-place swap preserves identity) — never tell users to drag a new DMG over the old app.
- **No live SQLite in iCloud** (corruption trap) — sync is per-asset JSON sidecars via `NSFileCoordinator`. CloudKit rejected (adds a network surface; the network paths are Sparkle + the opt-in Drive publish).
- **iCloud sidecars: the analyze pass MERGES with the on-disk sidecar; manual tag edits re-export WITHOUT merging.** `writeSidecarIfICloud(mergeExisting: true)` protects another device's manual tags from a blind vision-only overwrite (`Sidecar.merge`: last-writer-wins scalars, tag union, manual-beats-vision); `TagStore` add/remove/delete-all/remove-label call `AnalyzePipeline.exportSidecarsAfterTagEdit`, which writes the DB state verbatim — merging THERE would resurrect a just-deleted tag from the old sidecar. Don't flip either mode. (Known gap: library-wide `renameLabel` has no URLs and doesn't re-export.)
- **A note's iCloud sidecar write is split by who owns the field: `Sidecar.resolveForWrite(fresh:existing:mergeExisting:noteAuthoritative:)`.** A note rides the SAME sidecar as tags, so an unrelated tag/rating/import edit (`mergeExisting: false`) would otherwise overwrite the whole sidecar and wipe a note another device wrote but this device hasn't hydrated. Only `TagStore.setNote` passes `noteAuthoritative: true` (via `exportSidecarsAfterTagEdit(for:noteAuthoritative:)`) — every other manual-edit caller leaves the on-disk note untouched (`out.note = existing.note ?? fresh.note`). The analyze path (`mergeExisting: true`) is unaffected — its `Sidecar.merge` note rule is already non-nil-beats-nil (`winner.note = b.note ?? a.note`, b=fresh), so a not-yet-hydrated note survives an analyze-export without needing the authoritative flag. Don't collapse `resolveForWrite` back to writing `fresh` wholesale on the manual-edit path.

## Tags, ratings & notes

- **Tags are per `(file_id, parent_dir)`**, not per content hash. A duplicate in another folder has its own tags; deletes never leak across folders; NO library-wide tag delete. Other content-derived metadata (palette/caption/dims/intent/feature-print/FTS) stays content-hash-keyed. Memory: `muse-tags-are-per-file-not-per-content-hash`.
- **Rating exclusivity has to survive SYNC, not just local writes (2026-07-28).** A rating is stored as a manual tag, and `Sidecar.merge` unions tags by label — so two devices that rated the same photo while offline merged to a sidecar carrying BOTH "★★" and "★★★", and hydration then materialized both into the local DB. `merge` now resolves the rating like the other SCALARS (newest `updated_at` wins, falling back to the older side when the newer carries none — union semantics never delete, and a genuine clear travels the manual-edit path that bypasses merge); `collapsingRatings` defends the materialize seam against a sidecar an older build already wrote with two; and `SidecarHydrator` skips a syncing rating when the file ALREADY has one locally, so a rating set on THIS device is never overwritten by a syncing one (same protection `NoteStore.applyHydrated` gives a newer local note). Any new path that turns sidecar tags into DB rows must keep the one-rating-per-photo rule. **The DB-side identity-merge helpers enforce it too (2026-07-29):** `Indexer.unionTags` (edit-in-place hash-collision re-home) and `FileMoveMigration.migrateTags` (in-app move) key their tag conflict on the EXACT label, so merging a scope rated `★★` into one already rated `★★★★` kept BOTH (distinct labels, no `UNIQUE(file_id,parent_dir,label)` clash) — two ratings on one photo, breaking `resolution` and leaking a two-rating sidecar. Both now call `Indexer.collapseRatings(db:fileID:parentDir:)` after the merge (highest run wins — the same deterministic tiebreak `Sidecar.collapsingRatings` uses, since `TagRow` carries no timestamp). Don't remove those calls, and route any new tag-merge helper through `collapseRatings`.
- **A star rating IS a mutually-exclusive manual tag** (label = a run of `★` U+2605, 1–5, per `(file_id, parent_dir)`) — so it inherits scoping/manual-beats-vision/filtering for free (`StarRating` owns the pure logic; `TagStore.setRating` is the ONLY write seam and enforces one-rating-per-photo via `StarRating.resolution`). Consequence: **every tag-LISTING surface MUST filter out rating glyphs** or the model leaks — `allTagLabels` (grid "Add Tag" menu) excludes them (offering `★★★` there would attach a SECOND rating, since `addManualTag` has no mutual exclusion), and the hero Tags card + its suggestions exclude them (the rating shows in its own RATING card, not duplicated as a tag pill). The tag-chip row (`TagChipLoader.ordered` front-sorts ratings) and the active-filter banner DO show them — that's the intended filter affordance. Badge display is gated by `AppSettings.showStarsOnGrid` (default on) which hides it on the MAIN folder grid only (still shows in collections + hero); the `starRatings` map itself is always computed (drives the context-menu checkmark even when the badge is hidden). A new tag-listing UI must decide explicitly whether to filter `StarRating.isRating`. **This applies to tag-WRITING surfaces too:** `MetadataImportApply.applyKeywords` (the Lightroom/Bridge keywords import) drops rating-glyph labels — an imported keyword that happened to be a run of `★` would otherwise become a second rating tag and break `resolution` (rating comes through the separate rating field, never as a keyword).
- **Every tag WRITE path must refuse rating glyphs, enforced at TagStore's seam (2026-07-28).** The listing surfaces already filtered `StarRating.isRating`, but the two free-text WRITE paths did not. (1) The chip row deliberately shows rating chips as a filter affordance and gave them the same `Rename Tag…` as any other chip — and rename is LIBRARY-WIDE, so renaming `★★★` to a word destroyed every three-star rating in the library in one write, with a confirmation that never mentions ratings. (2) The hero's "…or create a new one" field accepted `★★★`, and `addManualTag` has no mutual exclusion, so the file ended up with two ratings and `StarRating.resolution` broke. Both now go through the pure `StarRating.allowsManualTag` / `allowsRename(from:to:)` inside `TagStore` (not per caller — the same reasoning that put the filter inside `TagSuggest.rank` and `MetadataImportApply.applyKeywords`), and `TagChipsRow` hides Rename on a rating chip rather than offering a dead item. Delete stays on rating chips: it clears that rating from the files in view, which is what it says. A new tag-write surface inherits the guard for free; don't move it back out to callers.
- **Tag and note search results MUST carry `parent_dir` (2026-07-28).** Both are per `(file_id, parent_dir)`, but `SearchService` mapped matches to bare `file_id` and `aliveePaths` then resolved a file to EVERY alive path — so a tag or note on the `/A` copy surfaced the byte-identical `/B` copy, which carries neither. That is the cross-folder bleed the whole per-location grain exists to prevent, showing up in the one place it wasn't enforced. `NoteStore.searchScopes` and the tag row fetch now feed a `matchedDirs` map that narrows the resolve. FTS and semantic hits are content-derived and legitimately folder-agnostic, so a file matched by either is explicitly left UNRESTRICTED (as is a tag row with a NULL `parent_dir` — an orphan can't name a folder, and narrowing to nothing would drop a real hit). Don't collapse the resolve back to file_id-only.
- **A per-file NOTE is per `(file_id, parent_dir)` like tags — never a `files`/content-hash column** (`files.content_hash` is UNIQUE, so one file in two folders could carry two different notes). Stored in the `notes` table (`v11_file_note`), read/written through the pure `NoteStore` (the tested seam) with `TagStore.setNote` as the `@MainActor` write path; `setNote` deliberately does NOT bump `tagsVersion` (a note has no grid surface). **Searched via `LIKE` (merged into `exactIDs`), NOT FTS** — `files_fts` is keyed by the immutable `files.id`, which can't represent a per-location value. **Because a note shares tags' `(file_id, parent_dir)` grain, it MUST follow tags through EVERY identity/folder-key rewrite or it's silently orphaned (data loss).** The three relocation paths carry it (added 2026-07-07 — each originally taught only `tags`): folder rename (`FolderRenameMigration` — the same stale-target pre-clear + prefix rewrite as `tags`), in-app move (`FileMoveMigration` → `NoteStore.carry`, same file_id re-scoped old→new dir), and the Indexer shared-row split/collision (`NoteStore.carry` scoped/copy-vs-move, `NoteStore.carryAll` for the sole-path union) — copy-vs-move by the SAME same-dir-sibling rule as tags, never clobbering a destination note (INSERT OR IGNORE). A NEW path that rewrites `parent_dir` or `file_id` must carry `notes` alongside `tags`/`collection_members`.
- **Bulk tag delete leaves `analyzed_hash` untouched** so the auto-tagger never resurrects removed tags; they return only via explicit Regenerate.
- **Bulk tag ops (Delete All Tags / Regenerate) scope to `tagSourceFiles`, NOT `currentFiles`.** `currentFiles` is the underlying FOLDER even while a collection is on screen (the grid renders `activeCollectionFiles`), so using it makes "Delete All Tags" hit the folder, not the collection the user is viewing — the same wrong-target class as single-tag delete (which already uses `tagSourceFiles`). The bulk dialogs say "in this view" (not "this folder") for the same reason — they're reachable inside collections.
- **Star-badge width: the compact "5★" form is used only when it's actually NARROWER (2026-07-28).** `StarRating.badgeLabel` collapses the ★-run when it won't fit, but at ONE star the compact form ("1★", 17.3pt) is wider than the run itself ("★", 10.5pt), so a one-star badge never collapses — doing so makes the overflow worse. The widths are MEASURED (`NSAttributedString.size`) and hard-coded so the helpers stay pure/testable; re-measure if the badge font changes. The budget is the tile's DRAWN width (`TileView.slotSize` → min-scale fit against `drawnAspectRatio`), not the slot: the badge lives inside the aspect-fitted stack, so a letterboxed Grid-mode tile would be over-budgeted by the slot width.
- **Tag/collection suggestions must exclude `StarRating.isRating` labels — enforced inside `TagSuggest.rank` itself (2026-07-28).** A rating IS a manual tag and `addManualTag` has no mutual exclusion, so an offered `★★★` gives a file two ratings and breaks `StarRating.resolution`. Putting the filter in the ranker (not each caller) is what keeps a future fourth suggestion surface safe. Matching runs on the LOCALIZED display term while the returned label stays the canonical English key (display-time-localization rule); ordering is a stable TOTAL order (prefix > substring, then count, then alphabetical) so the list can't reshuffle under the cursor between keystrokes. The hero viewer's tag pool queries `LIMIT 500`, not the ~12 it displays — capping the query at the display count makes everything outside the most-used dozen unfindable, the exact near-duplicate the feature prevents. **Committing an existing collection NAME adds to that collection rather than minting a same-named twin** (`confirmNewCollection`, case-insensitive, manual collections only — a smart collection's membership is rule-driven so hand-adding wouldn't stick).
- **The tag chip filter is an ORDERED SET, not a scalar — `activeTagPaths` is the INTERSECTION (AND).** `activeTagLabels: [String]` (insertion order drives the banner). Mutate ONLY via `setActiveTags` (core — clears selection, recomputes `activeTagPaths` as the intersection) / `setActiveTag` / `toggleActiveTag`. **`setActiveTags` resolves the WHOLE filter SYNCHRONOUSLY** — it commits `activeTagLabels` AND reads each tag's paths (`pathsForTagSync`, a sync main-thread DB read) to set `activeTagPaths`, all in the click's own runloop turn, so the filter bar and the grid swap land in ONE render. A token-guarded async Task (the old design) committed the labels a frame BEFORE the paths, so the just-appeared bar shoved the still-unfiltered grid DOWN before the query returned — the "slide down, then replace" jag. The sync read can only ever wait behind one per-file write on the serial queue (a few ms; there are NO bulk write transactions to block on), and serial resolution also kills the old fast-Cmd-click stale-read race. Each per-label query stays `parent_dir`-scoped. `singleActiveTag` (count==1?first:nil) gates the single-tag menu commands. Empty intersection is a legitimate empty grid (only the single-tag case falls back to "All"). Chips + filter also mount/apply during SEARCH (search-aware `tagSourceFiles`/`reloadTagChips`). `EscapeResolver` `.clearTags` is ordered after search, before collection back-out. **The active-filter bar (`TagChipsRow`, below the chips) MUST render straight from `activeTagLabels` and show for 1+ tags — NOT gated on the scope's chips or a 2+ threshold.** Tags carry over into collections, so a single tag, or tags ORPHANED into a collection with none of them, would otherwise leave an empty grid with no on-screen sign a filter is active and no way to clear it (owner-reported bug). Each pill's ✕ removes one (`setActiveTags(TagSelection.removing(…))`); Clear all = `setActiveTag(nil)`. Don't re-add a visibility threshold or scope the bar to in-scope chips.

## Search

- **Search tokens are parsed from the COMMITTED field text, before every other leg (2026-07-31).** `SearchQueryParser` is the only tokenizer; an unknown key or invalid value is NOT a token and stays in free text verbatim (typed text is never silently dropped). `PhotoSearch` resolves tokens to an AND intersection over INDEXED columns only — it never opens a file, calls Vision or geocodes. `.text` folds into the free-text leg and `.color` into the EXISTING palette leg rather than getting a second matcher. **Rating tokens carry `parent_dir` restrictions and those are merged in AFTER the FTS/semantic relaxation step**, so a text hit on a byte-identical copy in another folder can't un-restrict a rating. A tokenless query is byte-identical to the pre-token pipeline (pinned by test); the unindexed-extras basename scan is skipped whenever tokens are present. Suggestions ride NATIVE `.searchSuggestions`; in-field NSTokenField-style tokens are explicitly not built.
- **Every file kind gets a basename `files_fts` row, not just analyzed images (2026-07-03).** `Indexer.reconcile` seeds it at all three new-row sites (+ `ensureBasenameFTS` on the resurrect/new-path branches), `analyzeOne` replaces it with the full row, and `v9_fts_basename_backfill` covered existing libraries. The backfill iterates a covered-ids Set — do NOT rewrite it as a correlated `NOT EXISTS` (files_fts.file_id is UNINDEXED → O(n²) inside the migrator = launch hang).
- **`AppState.searchQuery` commits ONLY when a search runs (`runSearchNow` / clear) — never per keystroke.** The field text is local `@State`; per-key writes to the `@Published` re-evaluated the whole shell. Consequences to preserve: EscapeResolver's `searchPresent` checks the LOCAL text too; `select(folder:)` bumps `searchDismissToken` (clears uncommitted text + pending debounce — searchQuery alone may already be ""); the scope toggle re-runs the FIELD text, not the committed query.
- **Search is native `.searchable(placement: .toolbar)`, NOT a custom toolbar item.** This is what gives the Notes/Mail behavior: the field pins to the far-right toolbar edge, COLLAPSES to a magnifier icon when the window narrows (expands on click), and lets the leading buttons roll into the `»` overflow — instead of the field vanishing. It's an `NSSearchToolbarItem` under the hood. Scope (All / This Folder) is `.searchScopes` (bound to `AppState.searchAllFolders`); the 250ms debounce + `AppState.searchQuery` push + programmatic query-injection are wired via the `.onChange`/`.onSubmit` handlers + `handleSearchTextChange`/`setSearchScope`/`runSearchNow` in `ContentView`. `searchText` is LOCAL `@State` (don't bind `.searchable` straight to `AppState.searchQuery` — per-keystroke `objectWillChange` re-evals the whole shell). Tradeoff accepted: the field follows the SYSTEM look, no mood tint (the old centered mood-tinted `NativeSearchField` / `SearchBar.swift` was removed 2026-07-02). See `docs/search-bar-fill-investigation.md` for why the old centered-fill variant was a dead end and why right-aligned `.searchable` is the answer.
- **The search scope bar is a titlebar ACCESSORY, not part of the toolbar — `ToolbarFade` must fade it too (2026-07-28).** The All / This Folder bar (`.searchScopes`) is a bottom-layout `NSTitlebarAccessoryViewController` (`AppKitAccessoryBarController` hosting a SwiftUI root, 36pt) that grows the titlebar container 52→88pt. `ToolbarFade` only ever touched `NSToolbarView`, so the bar stayed lit over an open hero viewer AND swallowed clicks aimed at its ✕. `chromeViews()` now returns the toolbar plus every `.bottom` accessory. Verified by dumping the live hierarchy — this area's rule is diagnose-by-instrumenting, never by reading code. Also verified: AppKit REMOVES and re-adds that accessory around focus changes, so a `didUpdate` guard re-asserts hidden while `lastIntentHidden`, and (measured) AppKit won't install it at all while the toolbar is hidden.

## Analysis pipeline

- **Analysis pause is SCHEDULING, never an off switch, and import runs are never throttled (2026-07-31).** `ThrottlePolicy` is a pure truth table (userPaused ∨ thermal serious/critical → paused; battery ∨ Low Power → reduced); `WorkThrottleStore.waitUntilRunnable()` SUSPENDS rather than returning false, which is what makes a pause resumable — the analyze pass keeps its claim, in-flight files finish, concurrency is re-read per spawn. Gated at both `analyze(folder:)` spawn sites and once per write chunk in `PhotoHeaderBackfill`/`GeocodeBackfill`/`DeepAnalysisBackfill` (`.utility` priority unchanged). `userPaused` persists (a pause that silently clears itself reads as broken); thermal/battery are live-only. Markers, selection logic and data paths are untouched — DECIDED #22 intact, there is still no analysis toggle.
- **The import-size FYI is one button, gated on a MEASURED estimate, at most once per launch (2026-07-31).** `AnalysisStatusStore` counts analyzable/pending off-main (≤1 query per 5 s, token-guarded) and keeps a NON-published per-file EMA; `AnalysisEstimator` refuses to estimate before `calibrationMinimum = 200` completions, because an M1 Air and an M4 Pro differ 3–4× and a hardcoded figure would embarrass itself on one of them. It fires only when the backlog GREW by a calibration's worth since launch and the estimate exceeds 25 minutes — below that, fully silent. Never a choice dialog, never a skip path. The status pill is untouched (background-work-only rule and inputs unchanged); progress lives in a Settings **Library** row and a sidebar footer row.
- **`files.feature_print` is the RAW `VNFeaturePrintObservation.data` element buffer — never `NSKeyedUnarchiver` it (2026-07-31).** `VisionServices` writes the bare Float32 array, never an archive, so the unarchive both call sites used returned nil for EVERY row: the duplicate finder's "Visually similar" mode and `SimilarTagSuggestions` had silently returned nothing since they shipped. All comparisons go through `Intelligence/Core/FeaturePrints.floats/distance` (vDSP Euclidean), which returns nil for length-mismatched pairs — prints from different Vision revisions must never pair. `DuplicateFinder.visualGroupIndices` is the extracted pure grouping pass so the fix stays pinned by a test that needs no Vision run.
- **The analyze pass decodes at a BOUNDED 4096px long edge (`VisionServices.analysisMaxPixel`) — never full resolution.** `loadCGImage` used `NSImage(contentsOf:)`, handing a full raster to five concurrent Vision requests; only feature print downsamples internally, so classify/faces/OCR/`CIAreaAverage` ALL scaled with pixel count. A 115 MP scanner TIFF cost **111 seconds and ~1 GB peak** per file against a then-serial loop (the reported "Muse hangs while analyzing TIFFs"); bounded it is 620 ms. Measured identical output at 4096 — same labels, feature print, dominant colour, face count, and **918/918 OCR chars on a document scan**. 4096 not 2048 because the extra decode is ~200 ms and a document at 1024 lost 25% of its characters. Don't raise it for "quality"; there is none to gain. `withinDecodeBudget` still runs FIRST (bomb guard) — bounding the REQUEST doesn't help formats ImageIO can't stream-downsample, which materialize the full raster anyway. **Don't re-add a format blacklist or an OCR probe**: both were designed, and the probe was BUILT and **disproved** — a `.fast` probe at 1024px read 0 of a real document's 918 characters.
- **Colour extraction is pinned to sRGB in BOTH `VisionServices.dominantColorHex` and `PaletteExtractor`.** `dominantColor` rendered with `workingColorSpace: NSNull()` + `colorSpace: nil` — no colour management — so it read whatever space the decoder returned as if it were sRGB. RAW decodes as **ITU-R 2100 PQ**, so RAW `dominant_color` was wrong, feeding colour tags + colour search. (Most of that error was actually fixed by the bounded decode, which returns P3/sRGB; pinning removes the remainder and makes correctness structural — the decoder's output space is otherwise a per-format lottery.) Don't set either back to nil/NSNull/DeviceRGB.
- **`PaletteExtractor.downsampledRGB(image:)` must use `.high` interpolation.** The analyze path hands in the 4096px raster, so this is up to a 128x reduction; `.medium` point-samples and aliases badly. Mean per-pixel error vs ImageIO's own 32px thumbnail: `.medium` 26–43, `.high` 2.6–12.6 (progressive halving scored the same as `.high`, so it isn't worth the extra passes).
- **Clustering is an exact tiled `vDSP_mmul`, NOT incremental.** `HybridClusterer` was all-pairs `VectorMath.cosine`, which recomputes BOTH magnitudes per pair — each vector's norm recomputed N times per pass, 50M comparisons at 10k files, after every analyze pass. Now: normalize once (cosine → dot product), one matmul per row tile. Measured 10x at n=500, 62x at n=2000, 96x at n=5000. Agreement with the scalar reference is exact **except** for pairs within ~3e-7 of the 0.62 threshold (3 of 12,497,500 at n=5000) where Float and Double rounding land on opposite sides of a tie — real but meaningless, and **NOT "bit-identical"; don't describe it that way.** `vDSP_mmul` not `cblas_sgemm` (deprecated from macOS 13.3 without a project-wide `ACCELERATE_NEW_LAPACK` flag). Tiling is memory-only (the full matrix is ~400 MB at 10k) — don't remove it. **Incremental/centroid clustering was rejected**: it's a different algorithm (no retroactive merge/split, order-dependent) whose failure mode is silent quality drift. `VectorMath.cosine` stays for `SemanticSearch`. Guarded by `SimilarityMatrixTests`, whose fixtures use CLUSTERED vectors — uniform random vectors are near-orthogonal in high dimensions, so no pair clears 0.62 and the equivalence assertion passes VACUOUSLY on two empty sets.
- **The status pill means BACKGROUND work only — thumbnails must never drive it (2026-07-28).** The one path that reported thumbnail work was the INTERACTIVE one (a visible tile fetching its image); the bulk prewarm reported nothing. So the pill was effectively a scroll detector: it appeared, filled and vanished on every scroll into un-prewarmed tiles (owner-reported as "shows, completes, then as I scroll does it again and again"). Thumbnails are no longer a `WorkProgress` phase and `ThumbProgress` is deleted; a loading tile has its own shimmer, which is where per-tile feedback belongs. Two related rules: a run ends only after `WorkProgress.idleGrace` (1.5s) of everything being idle, because the phases hand off with sub-second gaps and treating the first idle instant as the end chopped one job into a dozen sawtoothing runs; and the tick that notices that window elapsing is bound to `isActive` (`.task(id:)`), never a free-running `Timer.publish` — as an always-on publisher it woke the main runloop 3×/second for the app's whole life. Don't re-add a thumbnail phase, and don't make the tick unconditional.
- **A file that can't be DECODED must still have `analyzed_hash` stamped (2026-07-28).** `analyzeOne` returned early when the tagger yielded nil, leaving `analyzed_hash` NULL — and `analyzePending` selects exactly that, so the file was re-queued on EVERY visit to its folder: pill up, futile decode, give up, forever (owner-reported as a folder that "does that every time"; found by the `MUSE_TRACE` phase log showing `analyzePending.run stale=1` twice within two seconds, then traced to a Fuji `.RAF` Apple's RAW codec can't open — `sips` reports no pixel dimensions for it either). `VisionTagger.analyze` returns nil ONLY when the CGImage load failed, which is a property of the bytes rather than a transient hiccup, so `markAnalysisAttempted` records the attempt against that content hash (no tags written) and the automatic pass stops retrying. It is guarded on the hash still matching, like the real commit, so a file edited mid-pass stays pending; and explicit Regenerate Tags still picks it up, since that targets files with no tags. Don't "simplify" the nil branch back to a bare `return`.
- **A pass that embedded nothing must not recluster** (`ReclusterGate`). Reclustering scales with LIBRARY size, not pass size; `analyze(file:)` used to rebuild the whole library after every single file.
- **The analyze loop is concurrent (3-wide) and progress is COMPLETION-counted, not index-derived** (`AnalyzeProgress`). Completion order ≠ index order, so the old `idx + 1` fraction jumped backwards. Cancellation stops new spawns and lets in-flight files finish, matching the old loop's `break`. The spawn logic is inlined, not a nested func — a local function inside the task-group closure does NOT inherit the enclosing `@MainActor` isolation and can't touch `shouldStop`/`current`.
- **`analyzeOne` captures the content hash BEFORE Vision and commits nothing if it changed mid-pass.** Stamping `analyzed_hash` from a commit-time re-read marks stale tags/caption as analyzed-at-the-NEW-hash — never repaired until the next edit. The write transaction guards `file.content_hash == analyzedHash` and the embedding + sidecar are skipped when it fails.
- **`AnalyzePipeline` passes serialize through `acquirePass()`, NOT a bare `while isRunning` busy-wait.** A sleep-gate wakes all waiters at once → two passes run + `cancelActivePass()` halts the wrong one. The fix: a synchronous `passClaimed` flag claimed with NO `await` between check and set (only the first woken waiter takes it); the claiming wrapper holds it via `defer` for its whole body. `analyze(folder:)`/`analyze(file:)` must NOT consult `passClaimed` (deadlock); cancel returns BEFORE the claim. **Every direct entry point that starts a pass must hold the claim:** the automatic paths go through `analyzePending`/`regenerateTagless`, and the manual menu/App-Intent paths go through `analyzeFolderManual`/`analyzeFileManual` — calling bare `analyze(folder:)`/`analyze(file:)` from a non-claiming caller lets a manual pass run concurrently with the automatic one (the exact bug the gate prevents).

## Thumbnails & decode budgets

- **Layout reads `EffectiveDimensions`; analysis and decode budgets read `ImageHeaderSizeCache` (2026-07-31).** `ImageHeaderSizeCache` stays the single orientation-applied truth for the ORIGINAL bytes; `EffectiveDimensions` is the crop-aware layer above it and is what every LAYOUT consumer calls (grid `drawnAspectRatio`, `HeroStage.resolveHeaderSize`, the Info card's dimensions row, `AspectRatioCache`'s DB + cold paths). The split is by QUESTION, not by file: the hero's >40MP mid-res gate reads `ImageHeaderSizeCache` DIRECTLY on purpose — it asks what the file costs to DECODE, which a crop doesn't change, and the effective size would understate it and skip the mid-res pass on exactly the files that need it. Same for `ThumbnailCache.declaredPixelCount`/`withinDecodeBudget` and `VisionServices`. `files.width/height`, `analyzed_hash` and `Indexer.reconcile` stay keyed on ORIGINAL bytes — an edit never changes content identity.
- **The thumbnail cache key carries the edit-stack hash, and `invalidate` drops BOTH stack states (2026-07-31).** The hash is appended to the key only when one EXISTS, so the unedited key is byte-identical to the pre-edit-aware one — otherwise every cached PNG in every library re-keys on upgrade and the whole grid re-thumbnails on first launch (`ThumbnailStackKeyTests` pins that equality). `invalidate(_:)` loops `renderedVariants × {current stack hash, nil}`: an edited file's PNGs are keyed by its hash and the original's by no hash at all, so dropping only one leaves live orphans that resurface the moment the edit is reverted. This composes with the existing rule that every requested size must be in `renderedVariants`.
- **`ImageHeaderSizeCache` stores DISPLAY dimensions (EXIF orientation applied) — it is the single orientation truth (2026-07-28).** Orientations 5–8 store a landscape buffer that shows portrait. `AspectRatioCache.imageIOAspect` always honoured that; the header cache and `files.width/height` (which reads it) did not — so an ANALYZED rotated photo packed at a different shape from an UNANALYZED one beside it, and the hero flight took off from a wrong rect. The swap lives in `ImageHeaderSizeCache.displaySize(width:height:orientation:)` and is applied in `resolve` and by `ThumbnailCache.declaredPixelCount`'s prewarm. Don't re-add a raw `kCGImagePropertyPixelWidth/Height` read anywhere that feeds layout, and note `files.width/height` are now display dims (matching Preview); the pixel COUNT for the decode budget is orientation-invariant, so `withinDecodeBudget` is unaffected.
- **Every thumbnail size a call site requests must be a CONSTANT listed in `ThumbnailCache.renderedVariants` (2026-07-28).** `invalidate(_:)` drops cached thumbnails by enumerating that list, and the cache key is path-based, so an unlisted variant survives an in-place edit and serves the OLD image forever — the on-disk PNG outlives launches. Two sites had already drifted: the Duplicates modal tile (its size was a private constant in the view, which is exactly how it drifted — it now lives on `ThumbnailCache` beside the enumeration), and the hero's undecodable-format fallback, whose size came from the VIEWPORT and so was unenumerable by construction (now quantized to the fixed `heroFallbackSizes` ladder, rounding up). A stale Duplicates tile is the dangerous one: that picture is what the user deletes on. Adding a thumbnail call site means adding its size here, and `ThumbnailVariantTests` fails if you don't.
- **Image decode is bounded by `ThumbnailCache.withinDecodeBudget` (300 MP header check) at every AUTOMATIC (no-click) full-raster decode site** — grid thumbnail (`imageIOThumbnail`), hero full-res, and the auto-analysis pipeline (`PaletteExtractor.downsampledRGB`, `VisionServices.loadCGImage`, `CollectionPDFExporter.imageIOThumbnail`). A tiny file can declare enormous dimensions (a few-KB PNG at 40000×40000 ≈ 1.6 Gpx); formats ImageIO can't stream-downsample (PNG/TIFF/BMP) materialize the full raster → OOM on folder open (prewarm) or on index (auto-tag). Header-only pre-check, overflow-safe, missing-dims→allow. A NEW auto-triggered decode of a user file must call this guard.
- **Thumbnail-gate permits are weighted by declared pixel count** (`DecodePermit`) — eight 115 MP TIFFs at once was GB of rasters on mere folder open. **`ThumbnailGate.releaseNow` must serve waiters in a LOOP**: one multi-permit release can unblock several small waiters, and serving one leaks concurrency until the gate starves. `DecodePermit.cost` does ceiling division as divide-THEN-adjust — `(pixels + unit - 1) / unit` TRAPS on overflow near `Int.max`, and the value comes from an image header (hostile or corrupt files reach it before `withinDecodeBudget` rejects them).

## Grid & layout

- **`visibleFiles`'s base is one line with three sources: `activeCollectionFiles ?? RediscoveryStore.shared.files ?? currentFiles` (2026-07-31).** A rediscovery surface is a content scope like a collection, so it gets teardown parity everywhere: `select(folder:)` dismisses it and Places, `removeRoot` re-resolves it against the new root set, opening any of Places/collection/rediscovery clears the other two AND the selection (the narrows-`visibleFiles` rule), and `dropFromActiveCollection` routes to `RediscoveryStore.drop(path:)` so a burn-deleted tile can't ghost back. Escape order is modal → viewer → search → tags → collection → **rediscovery** → collections page → **places page** → none.
- **Grid must stay virtualized.** No custom SwiftUI `Layout` or non-lazy container over the full file set — it materializes every tile + relayouts O(n) per publish (1700-image folders died). Use `MasonryGeometry` frames + a manual viewport window. Memory: `muse-grid-must-stay-virtualized`.
- **Photos never draw a card; the ring/hover/badge hug the DRAWN photo rect, not the slot (2026-07-28).** An image tile's content stack is fitted via `.aspectRatio(_, contentMode: .fit)` — the same min-scale fit as `ViewerGeometry.fitWithin` — so in Grid mode (square slots) the selection ring, hover veil and star badge wrap the visible image instead of boxing empty air. `tileFrames` reports that FITTED rect: `HeroStage` runs `fitWithin` on it and fitting an already-fitted rect is the identity, so the flight endpoint is exact instead of depending on two caches agreeing. The drawn aspect comes from `ImageHeaderSizeCache` (the hero's own table) with `AspectRatioCache` only as a cold-start fallback — don't swap the priority, and don't "restore" `tileFrames` to the slot rect. With no fill the empty slot area isn't hit-testable, so the tile carries an explicit `.contentShape(Rectangle())` at the slot size: ring and hover hug the photo, the click TARGET stays the slot. Removing it makes a click beside a photo fall through to the background and clear the selection. Transparent PNGs are drawn fully transparent by design (no auto-backdrop, no toggle).
- **`ImageLayout.resolve` MUST map the legacy raws — `"masonry"` → `.columns`, any `r*` → `.grid` (2026-07-28).** The ten fixed ratios and the masonry default are live on users' disks; the unknown-value fallback would silently drop a ratio user into Columns, a visibly different layout. `ImageLayout.aspect` is deliberately KEPT (`nil` for Columns/Rows, `1` for Grid) — the parting-ripple damping and the PDF exporter both read it as "is this a uniform lattice?". The `TileBackground` setting was deleted with the ratios (it only ever coloured the letterbox); non-photo tiles keep a card in the mood's tile colour via `AppState.tileFill`.
- **Rows layout = `JustifiedRowsGeometry`, and its trailing partial row is NOT justified.** Stretching it blows a single leftover image up to a full-width panorama. Per-item aspects are clamped to `[0.1, 10]` for PACKING only (a pathological panorama would otherwise force a sub-pixel row height) — the image still draws at its true shape. The target row height is derived from the images-per-row slider (`(width - spacing×(cols-1)) / cols`) so one control drives all three modes. **Spacing and corner radius live in Settings → Grid, not on the floating capsule** (zoom is the only floating control), and spacing's floor is a real gap, never 0 — flush-packed images read as one continuous picture rather than a grid. The PDF's `CollectionPDFLayout.paginateRows` consumes the SAME `rows(...)` output and only decides page breaks, which is what keeps print matching screen; don't fork the packing.
- **Grid tiles carry a file-stable `.id(file.url…path)`; the tile `ForEach` is index-keyed (`id: \.self` over `visibleIndices`) for virtualization.** Without the per-tile `.id`, a reorder (an in-place edit bumps `modified_at`, the date sort floats the file up) rebinds a slot to a different file while SwiftUI reuses the cell — and the cell's decoded `@State` thumbnail outlives the rebind, showing one file's image on another file's tile until a full remount (folder switch). The path-keyed `.id` forces a clean remount on rebind (never a stale bitmap); keyed on the PATH (not content) so an in-place edit of the SAME file still refreshes via the tile task's content-version id, not a remount. Don't remove it or re-key the `ForEach` off index without preserving file identity (`GridView.masonryCanvas`).
- **The async (Color/Shape/Rating) `resort()` publish must stay behind ALL of: `resortToken` + `folderLoadToken` + `collectionRequestToken` + `searchRequestToken`/`!isSearchActive`, AND publish the intersection with the live grid.** Those sorts read the DB off-main (Rating via `RatingLoader`, per-`(file_id, parent_dir)` scope; highest-rated first, unrated last); a stale result landing after `runSearch` overwrites ranked results, and direct removals (burn-delete, hero delete, removeRoot) bump no token — only the intersection keeps a trashed tile from resurrecting. Additions always arrive via token-bumping paths (reload / onRestore→resort), so the filter can't drop them.
- **The grid's LEFT/RIGHT margin IS the spacing value, and the spacing slider must NOT animate the relayout (2026-07-29).** `GridView.horizontalInset` returns `spacing` so the window-edge gap matches the inter-tile gap at every setting (ceiling 40); every width derivation must read it, since a site left on the old 20pt constant sizes the canvas differently than the padding reserves and pushes the last column under the edge. Top/bottom stays a fixed 20 — that edge is governed by the floating-toolbar clearance reserved above the scroll view. The `gridSpacingSetting` onChange is deliberately un-animated: it fires on every tick of a continuous drag, and a 0.25s curve per tick left tiles interpolating toward a target that kept moving, so they curved past each other instead of tracking the handle. Discrete controls (column count, layout) keep their animation.
- **The toolbar subfolders Toggle binds through `toggleSubfolders()`, not `$showSubfolders` + `.onChange`.** The direct binding wrote the value and the handler flipped it AGAIN (double-drive: extra reloads + a selection clear on the widening direction). `toggleSubfolders()` is the single owner of the flip and its side effects; the Toggle uses a custom Binding whose set ignores the incoming value.
- **The grid's wholesale-swap `.id` must key on the RESOLVED filter (`tagFilterGeneration`), NOT `activeTagLabels`.** `activeTagPaths.didSet` bumps `tagFilterGeneration` in lockstep with the resolved set; the grid keys on that. (Historically labels and `activeTagPaths` landed in different frames — paths via an async query — so keying the `.id` on labels rebuilt the canvas early and flashed the PRIOR tag's files until the query returned, the switch flicker. `setActiveTags` now resolves synchronously so both land in one frame, but keying on the resolved generation is retained as the correct, gap-proof rule.) And the swap is **`.transition(.identity)`, not `.opacity`** — outgoing/incoming canvas read the same global `visibleFiles`, so a symmetric opacity fade dims two identical layers to ~75% and back (a visible blip, not a real cross-fade — shared state can't give one without snapshotting). `.identity` is required (an `.id` change inside `withAnimation` defaults to `.opacity`); don't "simplify" it away. Tag/collection switches are now an instant replace by design. **Folder switches follow the same rule:** the fresh-select reveal in `reloadCurrentFiles` (the `freshSelect` branch) commits `tagChipRows`/`tagRowReady` WITHOUT `withAnimation` so the new folder hard-cuts in (tab-switch feel), not fade in — don't re-wrap it; the fade was a perceived "lag after click." Files + chips still commit in one `MainActor` transaction so the "images appear already in place below the chips" ordering is preserved.

## Hero viewer

- **Hero open/close toolbar is a WINDOWED/FULL-SCREEN HYBRID — do not unify it (2026-07-06, hard-won over many rounds).** WINDOWED uses `ToolbarFade` (AppKit alpha fade on the always-mounted `NSToolbarView`), NOT `.toolbar(.hidden, for: .windowToolbar)`: the SwiftUI toggle tears down/re-materializes the native NSToolbar — that re-materialization was the "empty nav, icons pop in late" close delay. ToolbarFade's fade-in is an explicit fast-start `CABasicAnimation` (`NSAnimationContext`'s ease measured back-loaded → reads as empty nav). FULL-SCREEN uses a SwiftUI `.toolbar(appState.selectedFile != nil && isFullScreen ? .hidden : .automatic, for: .windowToolbar)` on the detail (`isFullScreen` tracked via didEnter/ExitFullScreen notifications): macOS relocates the full-screen toolbar into a separate auto-hiding `NSToolbarFullScreenWindow` the AppKit fade can't reach, so `ToolbarFade.toolbarView()` bails on a `.fullScreen` window (both calls no-op there) and SwiftUI owns the full-screen hide. **The dormant `.automatic` in windowed adds a slight windowed close delay — this is an ACCEPTED, owner-signed-off tradeoff.** Every attempt to remove it failed: `NSToolbar.isVisible` in full-screen reclaims layout → the hero image/tags SHIFT (rejected); a conditional (if/else) `.toolbar(.hidden)` FLICKERS the grid/sidebar on open wherever attached (rejected); dropping the SwiftUI modifier entirely makes the full-screen toolbar stay visible over the hero (rejected). There is NO version with both perfect-windowed AND full-screen-hidden; don't re-litigate. ToolbarFade also tracks `lastIntentHidden` + re-asserts on `didExitFullScreenNotification` (the hidden alpha carries back to the windowed view across a full-screen round-trip). The close "flash" (2026-06-18, long misattributed to the toolbar) was really the hero BACKDROP unmounting before its 0.4s fade-out finished: its out-animation is **0.3s on purpose** (in stays 0.4s), must stay under the 0.36s unmount — don't re-symmetrize. **Escape must fire ONLY `viewerClosing = true`** and let `startClose()` own the whole close (incl. setting `viewerDismissing`), exactly as the X button does — a separate `viewerDismissing` write in the Escape path made Escape need TWO presses.
- **The hero flight starts/lands on the tile's DRAWN-IMAGE rect (`ViewerGeometry.fitWithin`), NOT the raw tile rect (2026-07-07).** Fixed-aspect (grid) layouts letterbox the image inside a differently-shaped tile, so flying to `sourceFrame` lands as a center-crop that visibly re-fits the instant the real tile reveals (the grid-mode close glitch). `HeroStage.sourceRect` = `fitWithin(headerSize, sourceFrame)`; `open()`/`close()`/the mid-flight `sourceFrame` retarget all use it. **The aspect comes from the FILE HEADER (`ImageHeaderSizeCache`), never the decoded `image` (2026-07-28)** — `image` is nil when the OPEN flight starts, so the old `image?.size ?? sourceFrame.size` fell through to `fitWithin(frame.size, frame)`, which returns the FRAME ITSELF: the flight departed from the raw tile rect, the exact thing this rule forbids. A landscape image letterboxes hard inside a squarer tile, so its real drawn rect is far shorter — starting from the tile rect made the flight too short (same duration, less distance), which reads as "almost instant" with a wrong curve; portrait letterboxes less and looked nearer right. That asymmetry is ASPECT GEOMETRY, not file size (an early diagnosis blamed the 115 MP fixture's size — it was also the only portrait one, a real confound). **The header read must NOT happen in `sourceRect` itself**: it's a computed property, re-evaluated every body pass — i.e. every frame of an animating flight — and it was memoized in an `NSCache`, which evicts under exactly the memory pressure a 659 MB image open creates, so an evicted entry meant a fresh 17.7 ms file open PER FRAME on main. Resolve it once into `@State` from `ImageHeaderSizeCache` (a never-evicting table the thumbnail pass warms off-main via `declaredPixelCount`, invalidated alongside thumbnails since an edit can change dimensions). Its stale-result guard must key on a `@State` URL, not `self.url` — an escaping closure captures a FROZEN copy of the View struct, so checking `self.url` is vacuous and an arrow-flip could land file A's aspect on file B. **And the mid-flight retarget must never GROW** (except from a degenerate zero-size target): a close only shrinks, and a transient grid relayout reporting a bigger frame animates the image back out. **`files.width`/`height` come from the header too** (`VisionServices.analyze`), NOT from `cgImage.width` — since the analyze decode became bounded at 4096px, reading the raster made a 9600x12000 scan report 4096x5120 in the Info card. In masonry the tile aspect already == the image aspect, so `fitWithin` returns the tile rect and nothing changes. Don't "simplify" the endpoints back to `sourceFrame`. The grid-side hero-open **parting ripple** (`PartingField`, neighbors shrink/ease away from the click) applies only to MOUNTED tiles (virtualization intact — see the grid-virtualization note) and only for hero-image kinds (image/raw/psd, the ones that fly); its close converge is `easeOut` (an `easeInOut`'s slow start read as stop-start jitter under the fade-in), and parted neighbors must NOT write their transform-warped `proxy.frame(in: .global)` into `tileFrames` (guarded — else an arrow-flip close flies to a warped rect). The star badge/letterbox-card reveal timings are layout-uniform on purpose (badge fades in at unmount everywhere; card returns at close-flight start) — a per-layout split read as inconsistent (owner-reported).
- **No post-decode `displayRect` write in `HeroStage.loadFullRes()` may run while `isClosing` (2026-07-28).** That function ends with `withAnimation { displayRect = fitRect }` — the write that flies the image out to full screen once the sharp decode lands. A 115 MP TIFF decodes in ~600 ms and an open-then-Escape closes at ~450–600 ms, so on big scans the decode routinely landed INSIDE the close flight, animated the shrinking image back out, and then the unmount snapped it away: the owner-reported "it closes, then reopens, then closes again", visible only on large files because only those decode slowly enough. All three exits guard on `!isClosing`, as does the intermediate mid-res swap (changing `image` mid-flight re-bases `fitRect`, the flight's layout `home`, and jumps the transform). Traced in the running app — the close state sequence is a clean single close, so the reopen was purely this geometry write.
- **Never write a `@Published` `AppState` flag inside `withAnimation` (2026-07-28).** `appState.viewerDismissing = true` was wrapped in one; the write re-evaluates the WHOLE shell (sidebar rows, every mounted tile, tag chips) and a global animation transaction makes SwiftUI build animated transitions for all of it synchronously. `sample` on the running app measured **282 ms of blocked main thread inside that one setter**, at close-flight start: the image froze part-shrunk with the backdrop still up then jumped, and on the biggest files the block swallowed the whole flight ("closes instantly with no animation"). Nothing needed it — the toolbar returns via `ToolbarFade` (AppKit alpha, `.onChange`-driven) and the tile reveal is a value-scoped `.animation(_:value:)`. Animate the CONSUMERS, never the AppState write.
- **Anything in the hero open/close path must be diagnosed by INSTRUMENTING THE RUNNING APP, not by reading code.** Across this view's bug history every reasoned fix was wrong (six attempts on the open flicker, three on the close stall, three on the reopen) and every instrumented one was right — `sample <pid>` for main-thread stalls, a `NSTemporaryDirectory()` timeline trace for state ordering (Muse is sandboxed: a `/tmp` path is silently denied, and NSLog did not reach `log stream` at all), env-var A/B substitution for compositing. Full record: `docs/hero-viewer-open-close-handoff.md`.
- **A later `withAnimation` on the same value REPLACES a running animation — the hero's post-decode `displayRect` writes must stay on the open spring (2026-07-29).** Every decode step (quick thumb → mid-res → sharp) re-writes `displayRect = fitRect`, and a normal image's sharp decode lands ~100–200 ms in, so a `withAnimation(.easeOut)` there swallowed the open bounce entirely. `HeroFlightMotion.settling(since:)` keeps those writes on the spring while it's still settling and falls back to a plain ease after (by then it's a correction, not the flight) — same class as the `isClosing` guard already documented in `loadFullRes`. The open curve is `.spring(duration:bounce:)`, NOT `.spring(response:dampingFraction:)`: the latter has no bounded settle, so damping high enough to tame the overshoot still crept past half a second — slow AND bounceless at once. An arrow-key FLIP is a re-fit, not a flight, so `flipTo` clears the settle window (otherwise the same keypress bounced or not depending on the user's timing). The close FLIGHT stays on its fixed 0.34s curve — the backdrop fade (0.3s) and unmount (0.36s) are timed against that number.

## Sidebar

- **Sidebar rows: never use `.onDrag`.** It installs an AppKit drag source on the shared hosting view and eats single-clicks. Reorder is a live `DragGesture` off a trailing grip + an opaque on-top overlay (both folder + collection lists).
- **Hiding the iCloud "Muse" sidebar root is EMPTY-ONLY, gated on the LIVE recursive file count — never the bare persisted bool (2026-07-06).** Settings → "Show iCloud Folder in the Sidebar" (`showICloudFolderInSidebarKey`, default on) lets a user hide the app-managed iCloud root, but ONLY while it's empty; a folder with files always shows (its Settings toggle greys out with a note) and reappears on its own the moment files land. Both surfaces — SidebarView's render gate AND the Settings toggle's disabled/footer state — route through the pure `ICloudSidebarVisibility` (`presence`/`rowVisible`/`toggleDisabled`) reading `folderStats.stat(for:)?.recursiveFileCount`, so they can't disagree; `nil` (count not yet computed) is treated as VISIBLE so the row never flickers out at launch. The gate lives in the `folderList` parent, which re-evaluates because `folderStats.objectWillChange` is forwarded to `AppState.objectWillChange` (AppState.swift ~589). Don't reduce the gate to the persisted flag alone (would hide a non-empty folder / fail to reappear), and don't drop the `nil→visible` rule.
- **EVERY sidebar row's geometry and colour comes from the shared constants on `SidebarView` — never inline a copy (2026-07-28).** Four surfaces draw this row shape (folder tree, collection, pinned folder, and the Symbol & Color modal's live PREVIEW, which stops previewing anything if it drifts). All read: `rowHorizontalPadding` (4), `chevronSlotWidth` (10, LEADING-aligned), `chevronToIconGap` (3), `iconToTextGap` (6), `treeIndentStep` (8, applied from the first nested level), `rowHeight`/`childRowHeight` (28/26), `rootIconSize`/`childIconSize` (12/11, one step only — a glyph that shrank per level is illegible three deep), `selectionFill`, `selectedLabelColor`. Rows are `HStack(spacing: 0)` + explicit per-element padding so one gap can be tuned without dragging the rest along. Load-bearing details: the slot is 10 because `chevron.down` MEASURES 10pt at 9pt semibold (`chevron.right` is 7) — narrower clips the expanded state; leading-aligned so the glyph sits 4pt from the selection edge, and `chevronToIconGap` is 3 not 6 because the slot's own slack already supplies 3pt of the visible gap; the chevron BUTTON keeps a 10×22 hit rect regardless of the small glyph. `chevronSlotWidth + chevronToIconGap` is the icon column's offset — change one and the whole sidebar moves together, which is the point.
- **Sidebar selection colours are the SYSTEM ones, measured — don't substitute `Color.accentColor` (2026-07-28).** Fill = `NSColor.unemphasizedSelectedContentBackgroundColor` (Apple's source-list grey, R220 light / R70 dark); label + icon = `NSColor.systemBlue` (R0 G136 B255 light — exactly #0088FF — / R0 G145 B255 dark). `Color.accentColor` resolves to `controlAccentColor`, measured at R0 G122 B255 in BOTH appearances: it does NOT adapt and reads muddy on a dark sidebar. Grey fill rather than the blue a focused `List` uses, because the label already carries the blue and blue-on-blue separates poorly. Accepted tradeoff: a non-blue system accent still shows blue here (it's a legibility colour, not a theme one). This sidebar is custom-drawn, so there is no native selection to inherit — these ARE the defaults, applied by hand.
- **Sidebar live-drag reorder must commit the new order SYNCHRONOUSLY, and the reorderable list must be a NON-lazy stack.** (1) The commit clears lift offsets in a `withTransaction(disablesAnimations)` block that ASSUMES the list is already reordered — so the reorder must land in that same synchronous transaction (folders get it free via `$roots`; collections update `CollectionsEngine.collections` sort_order in place synchronously, then persist async). (2) A reorderable `ForEach` must be a plain `VStack` by stable id, NOT `LazyVStack` over `Array(enumerated())` (which makes a reorder read as insert/remove and fly rows in). Animate with a list-scoped `.animation(_:value:)`.
- **A `LazyVStack` row list inside a shared `ScrollView` can de-materialize and not come back — use a plain `VStack` for short sidebar lists.** The FOLDERS section's `LazyVStack` could drop off-screen rows on scroll and leave the section empty (not data loss — `rootNodes` intact). `folderList` is now a plain `VStack` by node id, like `collectionsList`. Short lists sharing a `ScrollView` gain nothing from laziness and risk the vanishing-rows glitch.

- **Edit-menu "Select All" is the STANDARD item, driven by `AppDelegate.selectAll(_:)` — don't add a custom one.** SwiftUI auto-generates a standard `Select All ⌘A` whose `selectAll:` routes through the AppKit responder chain; the SwiftUI grid is no responder, so the app's lone `NSApplicationDelegate` (`@NSApplicationDelegateAdaptor`, the terminal chain link) implements `selectAll(_:)` → `appState.selectAllVisible()` + `validateMenuItem` (enabled on non-empty `visibleFiles`). A focused search field's field editor still wins ⌘A for its text (it's higher in the chain). A second, custom `Button("Select All")` produced a confusing duplicate (one greyed system item + one working custom) — that's what this replaced; never re-add it, and don't delete the `AppDelegate` (it also returns `applicationSupportsSecureRestorableState = true`). "Deselect All" (⇧⌘A) stays bespoke (no system equivalent).
- **Toolbar pills: `ToolbarSpacer` works ONLY in the trailing (`.automatic`) section, and ONLY in a FLAT builder.** On macOS 26 adjacent toolbar items fuse into one glass capsule; the split is `ToolbarSpacer(.fixed)` between items — but it's silently IGNORED between `.navigation`-placed items (three shapes verified live), and ANY `if #available` inside a toolbar content builder erases the group breaks too. - **Every modal footer button is `ModalButton` (2026-07-28).** There were three: a `FooterButton` private to the rules card, a `HoverButton` private to the Drive form (borrowed by Settings), and stock SwiftUI buttons everywhere else — so whether a card's buttons lit on hover depended on which card you opened (stock macOS buttons highlight on PRESS only, the odd one out in an app whose every other control responds to the cursor). Both old types are deleted. Three kinds: `.normal` / `.prominent` / `.destructive` (red — the confirm on an unrecoverable action). Disabled comes from `@Environment(\.isEnabled)` so a caller's plain `.disabled(…)` dims it — same reason `moodToolbarIcon` reads that value rather than taking a parameter. `title` is a plain `String`, so literals need `String(localized:)` at the call site.
- **…and never `.alert`/`.confirmationDialog` either (2026-07-28).** A system alert centres over the WHOLE window and dims nothing, so every confirm/error read as a different, app-level layer next to the cards. All 20 are now `ModalMessageCard` (confirm/error) or `ModalPromptCard` (the five name prompts) presented at the shell. Two ways in: `AppState.alertRequest` (a `MuseAlert`) for anything raised from a view that can't present — a sidebar row, a tile, or **another modal's content** — and `.museAlert(isPresented:)` for the shell's own error flags. The alertRequest presenter is attached LAST in the detail chain on purpose: it must draw ABOVE the card that raised it (a delete confirm over Duplicates), and `dismissTopModal` peels it first for the same reason. Every one of these new states is in `modalPresented` — as system alerts they had their own window, so the grid couldn't take keys behind them; as cards they must gate the key catcher. **A request FLAG must be consumed where it can't be missed:** the three tag confirms are raised from `TagCommandAlerts` at the shell, not from `TagChipsRow` which owns the chips — the row is absent on the Collections page and the menu bar can set those flags from there, and an `.onChange` with no mounted consumer leaves the flag stuck (the next request is the same value, fires no change, and the command is dead for the session). A state-bound `.alert` used to recover on remount; an onChange-raised card does not. Prompt drafts stay in LOCAL `@State` **inside the card** (the card is built only while presented, so it seeds itself on appear — the old external draft + `.onChange` re-seeding is gone). Wording literals were kept verbatim so no `.xcstrings` key changed.
- **Modals are IN-WINDOW cards, never `.sheet` (2026-07-28).** A sheet gets its own window, so its height can only be capped by reading the parent — and an AppKit view can't find that parent until it's inserted into a hierarchy, one runloop AFTER the first layout. That frame drew at the ideal height, spilled past a short window's bottom edge, and the measurement then snapped it back (owner-reported: "extends out then clips to be inside"). `.museModal(isPresented:width:palette:)` (`Views/Modal/`) renders a scrim + centred card inside a `GeometryReader`, so the card's height is a `maxHeight` CAP resolved during the first layout — nothing to measure, nothing to snap. Consequences to preserve: **every modal is presented at the SHELL** (`ContentView`), never from a sidebar row or toolbar button — a card is sized from its host's geometry, and a 240pt row would size it to 240pt, which is why collection-scoped modals hand their payload up via `AppState.collectionModal` (`CollectionModal`). The presenter measures the content's natural height from inside its scroller and gives the scroller that height clamped to the window, disabling scrolling while it fits. Do NOT reach for `ViewThatFits` here: it builds every candidate to measure them, and these cards have side effects on appear (Metadata Import starts a folder import, Manage Drive Shares hits Drive, the share form creates an upload service) — and asked for an IDEAL height it resolves to its greedy candidate anyway, which was verified failing twice in the running app. A modal's content must therefore be naturally sized: no inner `ScrollView`, and a `Form` needs `.fixedSize(horizontal: false, vertical: true)`. Duplicates lost its user-resizable window in the move (accepted).
- **`ToolbarContentBuilder.buildBlock` tops out at 10 elements — `plainLeading` is split in two for that reason alone.** Both halves are applied adjacently at the call site, so the rendered order is identical to one flat list. Adding a toolbar item means checking the count, not just appending.
- **The Symbol & Color modal's two tabs are ONE box, enforced by `CollectionPickerLayout` + its tests (2026-07-28).** Switching tabs must not resize the card. Both grids use FLEXIBLE columns so each spans exactly the width it's given — a fixed-column `LazyVGrid` is only as wide as its cells happen to total (ragged gap on the right) and silently OVERFLOWS the card when they total too much, which is what made the modal appear to change width. The usable width is `cardWidth - cardPadding*2` = 424 — derived in `CollectionPickerLayout.contentWidth`, never restated, since restating it is what made both tabs overflow by different amounts. (It was 408 while the presenter reserved a 16pt scrollbar channel; that channel was removed 2026-07-28 — it applied whether or not a card scrolled, so every modal sat visibly off-centre. The overlay scroller floats over the content instead; don't re-add a global reserve.) Catalogs are sized to divide evenly into their grids (42 symbols = 7×6, 66 emoji = 11×6) so neither ends ragged, and `pickerHeight` reserves the taller tab's height (under-reserving spills the grid over the buttons, which reads as a resize even though the frame never moved). The tests assert width equality EXACTLY and fail on a ragged row — change a catalog and they'll tell you.

## SwiftUI patterns, animation & AppState

- **`AppState` is frozen at the `@Published` surface (2026-07-31).** `PlacesStore`/`RediscoveryStore`/`StacksStore`/`SearchFacets` are Pattern B singletons; the ONLY integration cost is one forwarded `objectWillChange` cancellable each in `AppState.init` (the `folderStats` shape) plus a methods-only `AppState+<Feature>.swift`. The rediscovery and stacks cancellables also call `invalidateVisibleFiles()` — those stores participate in the memo, so a change of theirs must drop it.
- **Fixed-viewport overlay effects:** per-element `.layerEffect`/`.visualEffect` is the wrong tool (breaks containers, only on-screen elements). The gradual-blur attempt was fully reverted.
- **No Metal shaders remain** (water + burn removed); `Effects/` holds only the opacity-fade delete modifier.
- **Never drive a perpetual animation with a global `withAnimation(.repeatForever)` in `.onAppear`.** The transaction stays live and leaks into ANY view repositioned in the same update cycle (most visibly the AppKit toolbar — `GridView`'s `ShimmerBand` drifted the toolbar icons). Use value-scoped `.animation(_:value:)` to confine the repeat to its subtree.
- **A `ScrollView` clips to its OWN frame — reserve floating-toolbar clearance ABOVE the scroll view, not as inner padding.** The toolbar background is hidden, so any scroll surface reaching the toolbar edge slides content under it. Inner `.padding(.top:)` scrolls away with content. Every top-level scroll surface (grid AND `CollectionsPage`) needs its own reserve, kept on the shared `TagChipsRow.noTagsTopClearance` constant.
- **The grid's arrow keys carry `.function` inherently — detect paging by KEYCODE, never by the `.function` flag.** In `PageScrollCatcher.keyDown`, the four arrow keys (123–126) are navigation-group keys and ALWAYS set `.function` (and `.numericPad`) in `modifierFlags`, even with no modifier held. So "plain arrow" MUST be judged against the meaningful set only (`[.command, .option, .control, .shift]`) — an intersection that INCLUDES `.function` makes every plain arrow read as modified. And Page Up/Down is detected by the dedicated keycodes (116/121) ALONE — physical Fn+Up/Down remaps to those keycodes at the OS layer — NOT by `(fn && arrowKey)`, which fired on every plain arrow (the shipped bug: plain ↑/↓ page-scrolled, plain ←/→ dead-forwarded). Plain arrows MOVE the highlight (`GridKeyboardNav`) + auto-scroll (`GridScrollReveal`); plain Space opens via the double-click path; Fn/Page keeps paging; all else forwards down the chain (⌘A etc.). Don't reintroduce a `.function`-based Fn test.
- **A menu style REPAINTS its label — `font`/`foregroundStyle` set inside the label are discarded (2026-07-29).** `.menuStyle(.borderlessButton)` overrode the sort glyph's font exactly the way it already overrode `foregroundStyle` (the note in `SectionSortMenu` predates this and was the clue): three rounds of shrinking the font moved only the invisible frame while the drawn glyph never changed. Styles go on the `Menu`; the sidebar sort glyph instead carries an INTRINSIC size (`SidebarSortGlyph`, an NSImage + `SymbolConfiguration`), which no style can override, plus an explicit `renderingMode(.template)` — the tint is what signals Manual order, and `isTemplate` alone failing would draw a black glyph with nothing to notice. Generalizes: when a visual change appears to do nothing, prove the value reaches the renderer before picking a bigger number.
- **Animate a tile's TRANSFORM and its OPACITY separately (2026-07-29).** One shared `.animation` on the grid's parting put opacity on the close converge's bouncy spring — a spring overshoots, so brightness ran past 1, clamped, and came back: a visible hitch mid-converge. Geometry bounces (`PartingField.convergeResponse`/`convergeDamping`, staggered by `closeDelay` ≤0.05s so it reads as a ramp and still fits the 0.34s landing — `PartingFieldTests` pins both); the fade is its own shorter ease (`convergeFadeDuration`). What must never come back is an easeInOut on the converge: its dead-slow START under the fade-in read as stop-start jitter. Moving immediately is the load-bearing property, not the settle shape.
- **A SwiftUI `.frame(minHeight:…)` CENTERS its child — reserved space needs `alignment: .top` (2026-07-29).** The Smart Collection card's rule list floated mid-reserve with one rule and drifted upward as rules were added, only settling at the top once they filled the 150pt. Any growable region with a min height that should fill top-down needs the explicit alignment; the min height itself stays, so the card doesn't shrink-jump between one row and two.
- **`withAnimation` does NOT animate an `@AppStorage`-backed change** — the UserDefaults publish lands outside the transaction (instant). To animate a persisted bool, back it with plain `@State` seeded from/written to `UserDefaults` via `.onChange`, or use value-scoped `.animation(_:value:)`.
- **Never bind a `TextField` (or any per-keystroke control) directly to a `@Published` property on the monolithic `AppState`.** Each keystroke fires `AppState.objectWillChange`, re-evaluating the WHOLE `ContentView` body (sidebar + tag chips + grid) — fast Macs hide it, but on slower Macs typing visibly lags. Hold the draft in LOCAL `@State` inside a small dedicated `ViewModifier`/subview and write to `AppState` only on commit (the alert's Create/Rename button). The dialog alerts do this via `NameCollectionAlert` / `FolderNameAlerts` (seed local `@State` on open with `.onChange`; folder drafts key on the request's `id` since `FolderNode` isn't `Equatable`, and closing always passes through nil so re-targeting the same folder re-seeds).
- **An explicit `.foregroundStyle` overrides SwiftUI's automatic disabled dimming.** `View.moodToolbarIcon` colors glyphs explicitly from the mood, so a `.disabled` control's icon stayed full color. Fix: `moodToolbarIcon` is a `ViewModifier` reading `@Environment(\.isEnabled)` and applying `.opacity(isEnabled ? 1 : 0.4)`. Don't pair a fresh explicit `foregroundStyle` with `.disabled` expecting auto-dimming.
- **Don't put an AppKit `NSViewRepresentable` inside a SwiftUI `.popover` whose CONTENT SIZE changes at runtime.** The grid filter's tri-state "Images" `NSButton` paired with an expand/collapse disclosure left a stale blurred layer snapshot (ghosting) — the AppKit subview blocks the hosting view's size invalidation. Fix: fixed-size popover (show all format checkboxes always). Keep such popovers fixed-size, or use pure SwiftUI for the dynamic part.

## Filesystem, roots & sandbox

- **`bookmarks.$roots` sink delivers synchronously** — don't add `.receive(on:)`; the non-animated reorder commit relies on synchronous delivery.
- **FSEvents:** the stream needs `kFSEventStreamCreateFlagUseCFTypes` or `eventPaths` is a raw `char**` (crash on first change).
- **A zero file count from an unlistable folder is not "empty" — read `FolderStat.knownRecursiveFileCount` (2026-07-28).** `FolderStats.compute` builds its counts from `contentsOfDirectory`/`enumerator`, both of which fail soft, so an unplugged volume or a not-yet-materialized iCloud container produced a perfectly ordinary `FolderStat` reading 0 files. `ICloudSidebarVisibility` has an `.unknown` state for exactly this, but it keys on a nil count and the stat could never BE nil — so an unreadable iCloud container read as `.empty` and the row hid itself, defeating the empty-only rule ("a folder with files always shows"). `FolderStat.reachable` now records whether the listing actually succeeded and `knownRecursiveFileCount` returns nil when it didn't; every consumer that treats zero as a fact reads that accessor. Same fail-closed class as `PathReconciler.rootReachable` and `Housekeeping`'s root guard: don't let a failed read masquerade as an empty result.
- **A folder may be a library root only once (2026-07-28).** `BookmarkStore.addRoot` returns the EXISTING root when the picked URL already resolves to one, and `load()` collapses duplicates already persisted. Two roots at one path drew two identical sidebar rows that BOTH highlighted on click (the selected-row test compares URLs) and both counted toward reorder indices and reachability. The merge rule is pure + tested (`RootDedupe.keepIndices`) and FAILS CLOSED: an unresolvable root is always kept and never counts as a duplicate — two bookmarks that both fail to resolve are two folders we can't see (an unplugged volume), not one folder twice. Same rule class as `PathReconciler.rootReachable`.
- **Folder/scope path-prefix checks need a trailing `+ "/"`.** A bare `hasPrefix` matches a sibling (`/a/Inspo` ⊂ `/a/Inspo Extra/x.jpg`). Every prefix test guards with `$0 == prefix || $0.hasPrefix(prefix + "/")` (`Housekeeping`, `CollectionStore.isUnderAnyRoot`, `ICloudZone`, `PathReconciler`, `FolderRenameMigration`, `SearchService`). Use the same rule for any new containment check.
- **`BookmarkStore.addRoot` must `activate(root)` BEFORE `roots.append(root)`.** Appending publishes `$roots`, whose sink rebuilds the sidebar synchronously; `rebuildRootNodes` drops any root whose `url(for:)` is nil, and that reads `accessedURLs` (populated only by `activate`). Activate-after-append silently drops the new root's node (last-added vanishes). Don't reorder back.
- **A trailing debounce with NO maxWait cap starves forever under a sustained event stream.** `FolderStatCache` rescheduled its 0.4s recompute on EVERY FSEvents under a root, so iCloud sync churn froze the sidebar count indefinitely. Fix: a 2.0s maxWait cap (pure `StatRecomputeScheduler`) — past the cap, flush immediately instead of rescheduling. Any debounce over an unbounded event source needs this.
- **Renaming a ROOT folder needs a one-time parent-access grant — the sandbox can't write a root's parent directory.** A security-scoped bookmark grants a folder's *contents*, not the right to rename the folder itself (renaming writes to its PARENT). So an in-place `FileManager.moveItem` of a top-level (sidebar) folder fails with a real permission error (`parent writable: false`). `FolderOps.rename` distinguishes this (`.parentNotWritable`) from a genuine `.ioError`; `renameFolder` responds by calling `BookmarkStore.grantParentAccess(forRenaming:)` (an `NSOpenPanel` pointed at the parent — "Grant Access" returns the shown dir), then retries the move under that transient powerbox scope and repoints the root bookmark. The parent grant is NOT persisted (Muse's library is the folder, not its parent). Subfolders (parent already in scope) never see the picker. Don't collapse `.parentNotWritable` back into a blind "you may not have permission" message — that hid the real cause and made it undebuggable. In one-level browse, `visibleFiles` contains `.folder` `FileNode`s, so a co-selected folder rides along in any flow built on `effectiveSelectionURLs`. Move-to-Trash + sidebar drop-to-move both skip folders (`kind != .folder`); `SelectionActionsMenu` filters via `fileURLs`. Folder ops live ONLY on the folder card's context menu. Any new selection action must decide explicitly whether it applies to folders (default for file-only/destructive: exclude).
- **Bookmark staleness is acted on, not ignored.** `Root.resolveURLReportingStale()` + `BookmarkStore.activate` re-mint + persist when the system flags stale (a stale bookmark keeps resolving for a while, then fails for good and the root silently vanishes); `StarStore.resolveURL` same. Pin bookmarks mint READ-WRITE (`.securityScopeAllowOnlyReadAccess` made trash/rename fail in exactly the pin-outlives-its-root case the bookmark exists for; legacy read-only pins upgrade when they go stale).

## Selection, duplicates, App Intents & accessibility

- **Duplicates modal never fully deletes a group** — ≥1 copy always kept. A file can be in several groups (byte-exact + filename + visual), so `DuplicateDeleteRules` checks EVERY group it belongs to, not just the first: emptying a group is refused (3+) or swaps (2-copy); cross-group pre-seed conflicts reconciled by `rescued`. Don't reintroduce a per-first-group check.
- **Any input that NARROWS `visibleFiles` must clear or prune the selection.** The selection `Set<String>` is independent of `visibleFiles`, and `effectiveSelectionURLs` rebuilds a URL for an off-view selected file (so a hidden file rides into Move/Collection/Tag/Share). Active-tag + collection-removal + collection-scope + folder-select + **search (`runSearch`, after the stale-token guard)** + **`toggleSubfolders`** (only on the OFF/narrowing direction — turning subfolders ON merely widens, so the selection stays valid) + **`removeRoot`** (on ANY root removal, not just the active one — a collection can span multiple roots, so removing a *non-active* root must also re-resolve the active collection so the grid stops rendering the removed root's now-unreachable tiles under a shrunk count, AND prune selection; both come free from re-calling `setActiveCollection(activeCollectionID)`, whose first line clears selection and which re-applies the reachability filter) + the **burn-delete `onRemove`** (drops the trashed path from `selectedFiles`) call `clearSelection()`/prune; `gridFilter.didSet` calls `pruneSelectionToVisible()`. A new filter/scope that can hide selected tiles must prune in lockstep. (Entering search, subfolder-toggle, root-removal [both the active-root-only prune AND the non-active-root collection ghost], and burn-delete each historically skipped this — fixed in the post-1.3.3 + whole-codebase + post-1.3.6 review passes. 2026-07-03 additions: the non-fresh `reloadCurrentFiles` publish — FSEvents live reloads + the Duplicates batch delete — now prunes too.)
- **App Intents must NOT read `currentFiles` right after `openFromIntent` — enumerate the folder URL directly.** `openFromIntent → select(folder:)` clears `currentFiles` and re-enumerates OFF-MAIN, so a value read in the same turn is empty. The duplicate/analyze intents go through `AppState.analyzableURLs(at:)` (enumerates the folder itself); don't "simplify" them back to reading the grid's `currentFiles` (they'd silently operate on nothing).
- **A mouse-only modifier interaction has NO VoiceOver equivalent — give it a parallel named `.accessibilityAction`.** VO activation can't reproduce a double-click timing window or Cmd/Shift-click. The grid tile's double-click-open + the tag chip's Cmd-click-add were both VO-unreachable until each got an `.accessibilityAction` routing through the same call the mouse makes. Branch by node kind where the mouse path does (tile open = `selectedFile` for a file but `openSubfolder` for a `.folder`). The right-click `contextMenu` is VO-reachable; a bare gesture is not.

## Working practice

- **Fix the code, not the dev DB.** The user's library is a disposable fixture; never ship one-off migrations to patch a corrupted local DB — fix forward code, validate by clean re-index. Memory: `muse-fix-code-not-my-data`.
